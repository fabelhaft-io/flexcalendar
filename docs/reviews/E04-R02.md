Mention both in the migration's comment and the README sentence about `calflex_api`.

Say instead that Zitadel and its configuration runner still use the bootstrap login locally and that no requirement gives Zitadel its own role yet.

## Brief (condensed)

Decisions of 2026-10-09, where the docs leave gaps: roles come from the cluster bootstrap `infra/dev/postgres/initdb/20-roles.sql` (plain `LOGIN`, passwords from the container environment, runs only on an empty volume), and migrations only `GRANT`/`REVOKE`, after a guard that the roles exist; `calendars.mode` stays `text` with `(mode = 'private') = (meta_envelope IS NOT NULL)`; `UPDATE (last_used_at)` on `device_credentials` is granted to `calflex_caldav` now; Zitadel stays on the bootstrap login. INV-03: every generated ID is `uuid DEFAULT gen_random_uuid()`. Tests use a shared helper (`test/support/postgres.mjs`) that starts a throwaway Postgres with Podman and mounts the real initdb directory; they fail, never skip, without Podman.
