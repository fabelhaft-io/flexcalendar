### Decisions this brief makes (the docs leave gaps; the owner can overrule)

1. **Roles are created by the cluster bootstrap, not by migrations.** Roles are cluster objects with secrets and `calflex_migrate` has no `CREATEROLE`. Locally the bootstrap is `infra/dev/postgres/initdb/20-roles.sql` (it runs only on an empty volume, so existing volumes need `make dev-reset`; E08 provisions production). I ran this on `postgres:18-alpine` with the unchanged E04-R01 chain; it works, and afterwards `public` and `sabredav` and all their tables are owned by `calflex_migrate`:

   ```sql
   \set ON_ERROR_STOP on
   \getenv migrate_pw CALFLEX_MIGRATE_PASSWORD
   \getenv api_pw CALFLEX_API_PASSWORD
   \getenv caldav_pw CALFLEX_CALDAV_PASSWORD
   SELECT format('CREATE ROLE calflex_migrate LOGIN PASSWORD %L', :'migrate_pw')
   WHERE NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'calflex_migrate')\gexec
   -- the same two statements for calflex_api (:'api_pw') and calflex_caldav (:'caldav_pw')
   SELECT format('ALTER DATABASE %I OWNER TO calflex_migrate', current_database())\gexec
   ALTER SCHEMA public OWNER TO calflex_migrate;
   ```

   The roles are plain `LOGIN`: no superuser, `CREATEDB` or `CREATEROLE`. The passwords come from the container environment (`postgres` service in compose, dev-only defaults in `infra/dev/.env.example`).
2. **The migrations only `GRANT` and `REVOKE`.** The first one checks that the three roles exist and fails with a message naming the bootstrap file and `make dev-reset`. Grants are explicit per table: no `ALTER DEFAULT PRIVILEGES` on `public`. For `sabredav`, grant on the existing tables and sequences and add default privileges, so later SabreDAV tables work. `REVOKE ALL ON SCHEMA public FROM PUBLIC`, then `GRANT USAGE` to the two service roles. `calflex_api` gets no `USAGE` on `sabredav`.
3. **`calendars.mode` is `text NOT NULL` here.** The enum and the "private only until Phase 4" check are E04-R03 (it converts the column). A check keeps `meta_envelope` consistent: `(mode = 'private') = (meta_envelope IS NOT NULL)`.
4. **`UPDATE (last_used_at)` on `device_credentials` is granted to `calflex_caldav` now**; the table is empty until Phase 4.
5. **Zitadel stays on the bootstrap login** (`caldav`, the cluster superuser): its DSN and the `zitadel-config` runner are not touched. The spec's "Zitadel keeps its own database and role" is left for E08; say so in `openQuestions`.
6. **No pending-member state yet.** E06-R09 adds what it needs with its own migration.

### What to build

- The bootstrap SQL above, and the compose/env wiring: `postgres` gets the three password variables; `api` connects as `calflex_api`; `caldav` gets a `CALFLEX_DATABASE_URL` as `calflex_caldav`; the `migrate` default URL becomes `calflex_migrate`. Every new variable is documented in `infra/dev/.env.example` (`make check-stack` enforces it). Update `infra/dev/README.md` and the volume sentence in `CONTRIBUTING.md`.
- The migrations for the 11 tables of the spec, one or a few files, each with a `down`. **INV-03:** every generated ID is `uuid DEFAULT gen_random_uuid()` (no identity or serial columns; E04-R06 checks this). Timestamps are `timestamptz`. Cascades: deleting a calendar removes its members, invitations, feed tokens and outbox rows (E05 deletes by calendar). Hints for the consumers:
  - `users`: `idp_subject` unique, `handle` and `email` unique case-insensitively (`lower(…)` indexes);
  - `calendars`: `owner_id` → `users`, `caldav_href` unique (the collection URI holds the calendar's UUID, E03 § Layout), `meta_epoch integer`, `created_at`, `updated_at`. **No name or colour column**;
  - `calendar_members`: primary key `(calendar_id, user_id)`, `role` limited to `owner|editor|viewer`;
  - `invitations`, `feed_tokens`: `token_hash bytea` unique, `expires_at` / `revoked_at`, `variant` limited to `full|busy`; `device_credentials`: the Argon2id hash as `text`, `last_used_at`, `revoked_at`;
  - `caldav_changes` (E03-R10 writes, E07 reads): `calendar_id`, `sync_token bigint`, `uid text`, `change_type` limited to `created|updated|deleted`, index `(calendar_id, sync_token)`;
  - `delegation_nonces` (E03-R01): `nonce text` primary key, `expires_at`, index on `expires_at`;
  - `audit_log`: `at`, nullable `actor_id`, `action`, `subject`, `detail jsonb`. **No event content** in any column or default (INV-01).
- Grants exactly as the spec lists them: `calflex_api` DML on its tables but only `INSERT, SELECT` on `audit_log` and nothing in `sabredav`; `calflex_caldav` DML on all of `sabredav`, `caldav_changes` and `delegation_nonces`, `SELECT` on `users`, `calendars`, `calendar_members`, and decision 4. Nobody but `calflex_migrate` can `CREATE` in either schema. What I ran: `calflex_api` can insert into a table granted `INSERT, SELECT`, and `UPDATE` and `DELETE` fail with `42501`; `calflex_api` reading `sabredav.calendars` fails with `42501` (no schema `USAGE`).
