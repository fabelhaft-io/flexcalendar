# Review — E04-R04 · Sidecar envelope table

- **Status: brief before run 1** (2026-10-10). No code on the branch has been reviewed. Branch `feat/E04-R04-sidecar-envelope-table`. Reviewer: Claude (orchestrator). Executor `agent`: the owner's merge is the only approval.
- The requirement text is the spec (D-06, ADR 0001 § sidecar). This brief adds checked facts and the decisions the docs leave open. Paths: `server/api/` only.

## What to build

1. **One migration** in `server/api/migrations/`, `<unix-ms>_event-envelopes.mjs`, the real time of writing (`date +%s%3N`), greater than `1791530686002`. Raw SQL through `pgm.sql`, with a real `down` (`DROP TABLE`). The table `public.event_envelopes`:
   - `calendar_id uuid NOT NULL REFERENCES public.calendars(id) ON DELETE CASCADE`; `uid text NOT NULL` (stock apps' UIDs are arbitrary); `recurrence_id text`; `envelope_sha256 bytea NOT NULL`; `epoch integer NOT NULL`; `envelope bytea NOT NULL`; `created_at timestamptz NOT NULL DEFAULT now()`.
   - **No surrogate `id`**: the requirement's column list is exact, and the unique key is the row's identity. (So E04-R06 has nothing here to exempt or check.)
   - `UNIQUE NULLS NOT DISTINCT (calendar_id, uid, recurrence_id, envelope_sha256)` under a name of your choice. A named constraint, so the tests can assert `error.constraint`.
   - Two checks, named: `octet_length(envelope_sha256) = 32`, and `recurrence_id ~ '^[0-9]{8}(T[0-9]{6}Z)?$'` (NULL passes). The second pins the two encodings in the database: a `TZID` spelling or a floating time can't be stored. It doesn't catch an impossible date; don't try.
   - Grants: `calflex_api` gets DML like the other API tables (E04-R02 § roles); `calflex_caldav` gets nothing (CalDAV never reads envelopes). No other table, grant or default privilege changes.
2. **The key function**, `server/api/src/recurrence-key.mjs`, exporting `recurrenceKey(property)` that takes an `ICAL.Property` named `recurrence-id` and returns the canonical text: UTC `YYYYMMDDTHHMMSSZ` for a `DATE-TIME` (a `Z` value or a `TZID` one), `YYYYMMDD` for `VALUE=DATE`. A floating `DATE-TIME` (no `Z`, no `TZID`) throws (INV-04). It uses `ical.js`, the API's single time and recurrence authority (INV-05, `02`); don't convert time zones by hand. No `node:crypto` in `src/`.
3. **Dependency**: `corepack pnpm --filter @calendar-flex/api add ical.js@2.2.1` (`saveExact` is on). Checked 2026-10-10: 2.2.1 is `latest`, ESM, ships its types (`dist/types/module.d.ts`), no dependencies, MPL-2.0, and `INV-07`, `typecheck` and `lint` pass with it added (scratch copy of `main`). If you can't produce `pnpm-lock.yaml`, say so in `openQuestions`; the reviewer generates it in a separate `chore(E04-R04)` commit.
   - Behaviour I ran on 2.2.1 with `Europe/Berlin` (it knows the zone with or without a `VTIMEZONE`): `RECURRENCE-ID:20261012T080000Z` and `RECURRENCE-ID;TZID=Europe/Berlin:20261012T100000` both give `20261012T080000Z`; `;VALUE=DATE:20261012` gives `20261012`. Read the value with `property.getFirstValue()`, test `isDate`, and convert with `convertToZone(ICAL.Timezone.utcTimezone)`.
   - **Do not write tests for DST gap or overlap local times.** The docs don't pin them and `ical.js` departs from RFC 5545 § 3.3.5 there: `TZID=Europe/Berlin:20261025T023000` (occurs twice) gives `20261025T013000Z`, the second occurrence, where the RFC says the first; `20260329T023000` (does not exist) gives `20260329T003000Z`, where the RFC says use the offset before the gap, `…013000Z`. List both in `openQuestions`; the reviewer files them against E12-R01 and E15-R02.
4. **Tests**, in three places:
   - `test/recurrence-key.test.mjs`, **no database**: the spellings above give one key, `DATE` gives its own, floating throws, a non-`recurrence-id` property throws. Build the iCalendar text in the test, parse it with `ICAL.parse`.
   - `test/event-envelopes.test.mjs`, database-backed (the helpers in `test/support/postgres.mjs`, as `schema.test.mjs`): a master (`NULL`) and an override with the same `uid`, each read back by its own `recurrence_id` (`IS NOT DISTINCT FROM`); a second master with the same hash fails on the unique constraint (that is `NULLS NOT DISTINCT` at work); the same master with another hash is accepted (D-06: the new row coexists until garbage collection); the two spellings of one instant, run through `recurrenceKey`, give one key, and inserting both fails on the unique constraint; a 31-byte and a 33-byte hash fail their check; `20261012T100000`, `20261012t080000z` and `2026-10-12` fail theirs; deleting the calendar removes its rows; `down` removes the table and `up` restores it.
   - `test/schema.test.mjs`: add `event_envelopes` to `apiTables` and to the cascade list near the end, so the existing role matrix (API gets DML, CalDAV nothing) and the deletion case cover it. Change nothing else in the file.
5. A short paragraph in `server/api/README.md`: the table, where the key function is, and that `recurrence_id` is canonical text, not a spelling.
