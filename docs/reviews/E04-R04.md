## My brief was wrong twice

1. "`typecheck` and `lint` pass with it added (scratch copy)": no file imported `ical.js`, so the check was vacuous. The implementer's `TS2834` is real.
2. "`ical.js` knows `Europe/Berlin` with or without a `VTIMEZONE`": my script had registered the `VTIMEZONE` in the global `TimezoneService` in earlier calls, so the later call "without" it still worked. `ical.js` ships no zone data. It resolves a `TZID` from the `VTIMEZONE` in the same document first and then from the global registry; an unresolved one becomes floating. The implementer's contract is the right one and I confirm it: a `TZID` resolves through the document's `VTIMEZONE` (or a registry the caller filled), and an unresolved or floating value throws instead of producing a key.

## Follow-ups for other requirements (also in `follow-ups.md`)

- **E12-R01, E15-R02:** the DST cases the docs don't pin. With the zone's `VTIMEZONE` rules, `ical.js` maps `TZID=Europe/Berlin:20261025T023000` (occurs twice) to `20261025T013000Z`, the second occurrence, where RFC 5545 § 3.3.5 says the first (`…T003000Z`); and `20260329T023000` (does not exist) to `20260329T003000Z`, where the RFC says use the offset before the gap (`…T013000Z`). The wire spec and its vectors must pin one answer for the Dart `timezone` package and `ical.js` alike.
- **E05-R07, E13-R02:** `recurrenceKey` needs a trusted source of IANA zones. `ical.js` has none, and stock apps often omit the `VTIMEZONE`, so such an object throws today. Don't register a client's `VTIMEZONE` into the global `TimezoneService`: one client could redefine `Europe/Berlin` for everyone.
- **E04-R05, E04-R06:** tests must not assume the newest migration is theirs (`down 1`); E04-R03's and E04-R04's were the first to break.
- **Renovate:** drop `--skipLibCheck` when an `ical.js` release ships NodeNext-clean declarations. `ical.js` is MPL-2.0.
