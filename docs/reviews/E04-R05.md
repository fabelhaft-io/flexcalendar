## Brief for run 1

### The requirement changed after your prompt was built

The coordinator builds the prompt's requirement text from `main`, so it still shows one table, `user_keys`, with the wrapped copies "by kind". **The owner decided on 2026-10-10 to use two tables**, and I amended the epic in this worktree (`docs/epics/E04-data-model.md` § E04-R05, commit `cd75ddc`; read it, it is the spec). This is not a contradiction to report. The reason: the public keys belong to a user, the wraps to a user and a kind, and one table would repeat the public keys in every kind row with nothing to keep the rows equal.

### The schema (one migration, with a real `down`)

Match the neighbours: `pgm.sql` in a template literal, text + `CHECK` for small enumerations (as `role`, `variant`, `change_type`), plain `REFERENCES` to `users` without cascade, `ON DELETE CASCADE` only from `calendars` and `calendar_members`.

- `public.user_keys`: `user_id uuid PRIMARY KEY REFERENCES public.users(id)`, `x25519_public_key bytea NOT NULL`, `ed25519_public_key bytea NOT NULL` (both `octet_length = 32`: libsodium's `crypto_box_PUBLICKEYBYTES` and `crypto_sign_PUBLICKEYBYTES`), `created_at timestamptz NOT NULL DEFAULT now()`. One row marks a user as key-capable (E13-R01).
- `public.user_key_wraps`: `user_id uuid NOT NULL REFERENCES public.user_keys(user_id)`, `kind text NOT NULL`, `wrapped_private_keys bytea NOT NULL`, `created_at`; `PRIMARY KEY (user_id, kind)`. Constraints, with exactly these names: `user_key_wraps_kind_check CHECK (kind IN ('recovery_code', 'escrow'))` (INV-12 and D-17: no `password` kind, nothing else) and `user_key_wraps_no_escrow_check CHECK (kind <> 'escrow')`, the Phase 1 gate that E14-R01 drops by name. Both are separate constraints so that dropping the gate leaves the kind list in force. The blob is opaque: `octet_length(wrapped_private_keys) > 0` and nothing else (its format is E12-R01's; size limits are the API's).
- `public.calendar_keys`: `calendar_id uuid NOT NULL`, `epoch integer NOT NULL` (as `event_envelopes.epoch`; no extra rule), `user_id uuid NOT NULL REFERENCES public.user_keys(user_id)`, `record bytea NOT NULL` (the sealed and signed CCK record, opaque, non-empty), `created_at`; `PRIMARY KEY (calendar_id, epoch, user_id)`; `FOREIGN KEY (calendar_id, user_id) REFERENCES public.calendar_members(calendar_id, user_id) ON DELETE CASCADE`. A removed member's sealed copies go with the membership, and a calendar's go with the calendar. The signer is not a column: the record format (E12-R01) carries it. If it turns out not to, say so in `openQuestions`.
- Grants: `calflex_api` gets `SELECT, INSERT, UPDATE, DELETE` on all three; `calflex_caldav` gets nothing (the CalDAV service never reads key material). No `GRANT` to `PUBLIC`.
- None of the tables has a generated `id`: no `gen_random_uuid()`, no other generator (INV-03). No crypto import anywhere (INV-07); the tests build fake keys with `Buffer.alloc`.
- The file name is the current epoch in milliseconds, greater than `1791643469785` (the last migration) and at least `1791654649000`. The migration goes last.

### Tests

New file `test/member-keys.test.mjs`, in the style of `event-envelopes.test.mjs` (`fresh`, `migrate`, `rejects`). Never print blob bytes: a Postgres check failure puts the whole row in `error.detail`, so wrap the insert helper as that file does. Postgres fires check constraints in name order (`user_key_wraps_kind_check` before `user_key_wraps_no_escrow_check`): assert `error.constraint`, not only the code.

1. `user_keys`: a 32-byte pair inserts and reads back byte-equal; 31 and 33 bytes fail on the length check, for each key; a second row for one user fails (`23505`); an unknown user fails (`23503`).
2. `user_key_wraps`: `recovery_code` inserts; a second one for the same user fails; `escrow` fails on `user_key_wraps_no_escrow_check`; `password` and `''` fail on `user_key_wraps_kind_check`; an empty blob fails; a wrap for a user without a `user_keys` row fails. After `ALTER TABLE … DROP CONSTRAINT user_key_wraps_no_escrow_check` (what E14-R01 does) `escrow` inserts, `password` still fails on the kind check, and one user holds both wraps.
3. `calendar_keys`: a record for a member inserts and reads back byte-equal; the same triple fails; a second epoch and a second member coexist; a user who is not a member of that calendar fails (`23503`), and so does a member without a `user_keys` row; removing the membership deletes that member's records and not another member's; deleting the calendar deletes all of them.
4. Roles, through `psql`-style connections as in `schema.test.mjs`: `calflex_api` has the four DML privileges on each table; `calflex_caldav` and `PUBLIC` have none (`has_table_privilege` and an executed denial `42501`).
5. Rollback: **do not assume your migration is the newest** (`down 1`): E04-R03's and E04-R04's tests broke on that. Use the pattern of the last case in `event-envelopes.test.mjs` (list `migrations/`, `up` to your position, `down 1`), and check that `down` leaves no table of yours and no other table touched, and that `up` restores them. Likewise no case may count "all tables" or "all constraints" except where `schema.test.mjs` already inventories them.
6. `schema.test.mjs`: extend only what lists every table: `apiTables`, the cascade list and the "down to zero" inventory. Check by running them, not by reading. Change nothing else there. The "ids" case counts tables with an `id` column, and yours have none.
