- **From the E05-R08 reviews, for later requirements:**
  - **E07 (ping fan-out) and the clients:** `GET /calendars/{calendarId}/changes?since=<token>` answers `{token, changes: [{uid, deleted, etag?}]}`: pointers only, no `ical` and no content, so the client fetches an object with `GET …/events/{uid}` and a tombstone has no `etag`. The token is opaque and bound to the calendar (base64url of `<calendar id>:<n>`): store it and send it back, never build one. A `since` that is malformed, names another calendar or is ahead of the collection is a `410`, which means "reload the collection" (call it without `since`). Without `since` the whole collection comes back as present objects. Every empty poll costs one extra tiny `PROPFIND` (the API refuses a token ahead of the collection by reading the collection's own number); a fan-out that polls many calendars should poll the outbox (`caldav_changes`) or skip calendars it already knows are unchanged. The returned token is always the one the `REPORT` carried, so a change landing between two calls is never skipped;
  - **whoever next touches the adapter or `sync-collection`:** a `403` with no `cf:` precondition out of `sync-collection` is read as SabreDAV's `valid-sync-token` refusal and answered `410` (`src/changes.mjs`, `refusedToken`). The adapter's `parsePreconditions` collects `cf:` names only, so if a later SabreDAV tells that refusal from an ACL `403`, read the `DAV:valid-sync-token` element instead. SabreDAV 4.7.1 accepts a sync number ahead of the collection and echoes it, and binds no token to a collection; the API does both checks itself, so keep `adapter.currentSyncToken` and the calendar binding if the backend changes;
  - **Phase 4 (Shared mode, stock apps):** a stock app's object name is not its `UID`. A tombstone is named from its object name when that is a UUIDv4, and otherwise from the outbox, only when the window holds exactly one deletion; any other tombstone is left out of the answer, which costs the client one full reload. Revisit it with the outbox as the source of truth for deletions;
  - **whoever writes a new in-stack suite (`server/api/test/integration/`):** the `api-test` image installs production dependencies only. `test/integration-imports.test.mjs` fails a suite that imports a package outside `dependencies`, or `test/support/problem.mjs` (it needs the dev-only `yaml`); so a problem body is checked there with plain assertions on `type`, `title`, `status` and `instance`, and its match with the spec's `Problem` schema stays with the unit suites.
