- **From the E13-R02 review, for later requirements:**
  - **E13-R03 (the client write path), E10-R06 (offline creates):** a Private create is **one** `POST /calendars/{calendarId}/events` carrying the client's lowercase UUIDv4 `uid`, the envelope (standard base64), its `epoch` and `envelopeSha256`; the API inserts the row before the skeleton (D-06). A content change is `PUT /calendars/{calendarId}/envelopes/{uid}` with `If-Match`. A Private `PATCH` that moves `start`, `end` or the rule without a new `envelopeSha256` is a `422` naming `DTSTART`/`DTEND`; re-seal and send both. An offline create replays the same request, so the `uid` and the sealed envelope are made before the device goes online;
  - **E13-R03, E10 (the read path):** envelopes are read in bulk by calendar, by `uid` list or by delta token (`GET …/envelopes`); a `uid` and a `since` together are a `422`. Check `X-CALFLEX-ENVELOPE-SHA256` against the envelope bytes before opening (`spec/crypto.md` §1.3);
  - **E07-R01 or a later operations requirement:** the 24-hour orphan sweep runs after each successful envelope write, for that calendar only, because the API has no scheduler; a calendar that stops being written keeps its orphans. Move the collector (`src/envelope-gc.mjs`, clock-injectable) to a periodic job when one exists;
  - **E13-R02's ceiling:** the 65,536-byte event-envelope limit is enforced in the API only, not as a `CHECK` on `event_envelopes.envelope`; add one with the next migration that touches the table;
  - **Phase 4 (Shared calendars):** a delta read reports a tombstone only for an object named as the lowercase UUIDv4 this API writes; a stock-app-named object is left out. Revisit when Shared calendars store such objects;
  - **E05-R07:** `recurrenceKey` now takes its instant from `src/zones.mjs` with RFC 5545's answers (`spec/crypto.md` §3.4, §5.2), and its test reads the two Berlin cases from `canonical-timing-v1.json`; use it for plans too.
