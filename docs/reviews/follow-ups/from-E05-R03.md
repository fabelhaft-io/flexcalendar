- **From the E05-R03 reviews, for later requirements:**
  - **E05-R04 (and every route that takes a calendar id):** `calendars.mjs` answers an id outside the canonical lowercase UUID shape with the 404 an unknown id gets, before the store is asked, because Postgres raises `22P02` for anything else and an unhandled `22P02` is a 500. Do the same for any other id taken from a path, and for an event `UID` over 200 characters (`calendarobjects.uid` is `VARCHAR(200)`; E03-R10's note). Reach CalDAV through `adapter.forUser(userId, { requestId: request.id })` and answer a refusal with `sendCalDavProblem`; a CalDAV `401` is now a `502` there (our delegation failed, the caller's token was verified), so a route never turns it back into a 401. Use `resolveUser` for `users.id`, as the calendars routes do; two tests fail if you write a second lookup. The `calendars` row and the owner's `calendar_members` row exist before the first `PUT` into a collection, so a test of E05-R04 creates the calendar through the API or inserts both rows first;
  - **E10-R02, E10-R04 (the clients):** the calendars operations take `If-Match: "<version>"` on `PATCH` (428 without it, 412 when stale; `*` matches any version) and answer `ETag: "<version>"` on create and rename. The generated Dart client does not expose response headers, so the app reads the version from the body's `version`. `metaEnvelope` is standard base64 of version `0x01`, the epoch as a big-endian uint32, a 24-byte nonce, the ciphertext and a 16-byte tag, at most 4096 bytes decoded, and the header epoch must equal `metaEpoch`; anything else is a 422 with a fixed body. Plaintext `name`/`color` on a Private calendar is a 422 too;
  - **E12-R01:** `spec/crypto.md` did not exist, so the envelope header is checked as ADR 0001 lays it out (`src/calendar-envelope.mjs`: `ENVELOPE_VERSION`, `ENVELOPE_FIXED_BYTES = 45`, `MAX_ENVELOPE_BYTES = 4096`). Re-check the constants and the layout against the wire spec when it lands. The epoch field is a uint32 while `calendars.meta_epoch`, `event_envelopes.epoch` and `calendar_keys.epoch` are `integer`: the API accepts 0 to 2147483647, so the wire spec should cap the epoch there or E04 widen the three columns;
  - **E05-R05, E05-R06 and any new multi-method path:** a known path under a method it does not register is a 405 with `Allow` (`src/allow.mjs`, built from Fastify's route table through `onRoute`); a route added later is covered without touching it. `allowFor` returns the first template that matches, which is harmless while no two templates overlap;
  - **E06 (sharing):** `GET /calendars` already lists every membership with its `role`, and `PATCH`/`DELETE` already answer 403 to a member who is not the owner and 404 to a non-member; E06 adds the other roles, not these checks. `Location: /calendars/{id}` names a path with no `GET` (it answers 405 `Allow: DELETE, PATCH`): add `GET /calendars/{id}` when a client needs one;
  - **whoever next touches the generator wiring (E02-R07's `Makefile` and `infra/scripts`):** `make gen` exits 0 when `swagger_parser` prints "No schemes were generated" and leaves `apps/mobile/lib/api` empty; `gen-check` only catches the wiped directory afterwards. The generator itself dies on a path-level `parameters:` list (1.45.0 casts every path-item member to a map before it skips the key), so keep path parameters on each operation, as the spec's comment says;
  - **the next reconcile PR:** `docs/epics/E04-data-model.md` § schema lists the `calendars` columns without `version` (added by E05-R03's migration `1791696000000_calendar-version.mjs`).
