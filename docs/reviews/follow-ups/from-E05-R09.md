- **From the E05-R09 review, for later requirements:**
  - **E05-R06, E05-R07 (E05-R05 did):** the resolver is `src/zones.mjs` (`instantOf`, `localOf`, `isIanaZone`, `vtimezoneFor`): use it for every instant computed from a `TZID`, never `ical.js`, which has no zone database and is wrong on a skipped and on a repeated single local time. A `{local, tzid}` time is written as the wall clock the caller sent with its `TZID` parameter, and the generated `VTIMEZONE` is embedded once per zone, in front of the events (a definition already there, a stock app's own, is never replaced). The `daily-skipped` family of the DST table is still `ruling: pending`: the resolver neither passes nor fails it, and the owner's ruling on RFC 5545 § 3.3.10 decides it;
  - **E10-R04, E09, E11 (zone data across components; E12's AAD binds `TZID` and wall clock, `spec/crypto.md` §3.5):** the zone database is whatever Node's ICU carries (tz 2026b on the pinned Node 24.17, ICU 78.3), and this review found a host with 2026e disagreeing on two zones (Casablanca after September 2026, Tehran in 1979). Dart's `timezone` package, the browsers' ICU and Android's `java.time` each carry their own version, so a rule change reaches the components at different times. Record the tz version the image carries (a `process.versions.tz` line at start-up or in `GET /healthz`'s build info), regenerate `src/iana-zones.mjs` when a zone is added (a zone tzdata adds later is refused until then; the safe direction), and let the clients take their instant from `parsed.start.utc` where it is present;
  - **E15-R03 or whoever revisits the embedded definition (the size of a definition and the horizon; E05-R05 did not need to):** an embedded `VTIMEZONE` lists every transition from 1970 to 2100 as `RDATE`s, 6 KB for Europe/Berlin, 7 KB at most, in every object that uses the zone. An `RRULE` observance would be a few hundred bytes but it re-expands through `ical.js`, which is wrong on two single local times; revisit it with the expander. The horizon makes a `{local, tzid}` write before 1970 or after 2100 a `422` (use `{utc}`); `ical.js` reads an instant before a definition's first change as offset 0, which no object this API writes can hit but one another client stored can;
  - **whoever next edits `serialise` in `src/ical-rmw.mjs` (E05-R07 or E15-R01's harness; E05-R05 did not):** the module's output ends with `END:VCALENDAR` and no final `CRLF` (observed on every object the API writes since E05-R04). RFC 5545 § 3.1 wants every content line, the last included, terminated; SabreDAV and the stock apps tolerate it, but a stricter reader may not, so append the `CRLF` and have the round-trip harness check it;
  - **E03-R09 (the guard):** the allow-list accepts a `TZID` parameter with no `VTIMEZONE` in the object (it names properties, not definitions); only the API's write path and E15-R01's round-trip gate hold "no `TZID` without its `VTIMEZONE`";
  - **E10-R02, E10-R04, E09 (the clients):** an event time is `{date}`, `{utc}` or `{local: "YYYYMMDDTHHMMSS", tzid}`; the zone name must be an exact-spelling IANA name (link names such as `Asia/Calcutta` and `US/Eastern` are accepted; `europe/berlin`, a Windows name or an unknown one is a `422`). `parsed.start`/`parsed.end` carry `{local, tzid, utc}` where the zone resolves, and `{local, tzid}` where it does not (a stock app's Windows zone). A nonexistent wall clock (02:30 on a spring-forward day) is accepted and read with the offset before the gap, a repeated one as its first occurrence; an end that is not later than the start, across zones too, is a `422`.
