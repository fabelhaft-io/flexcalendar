- **From the E10-R01 review, for later requirements:**
  - **E10-R11 (the Play internal track):** the `release` build type still signs with the debug key, as `flutter create` leaves it (`android/app/build.gradle.kts`, "TODO: Add your own signing config"). Give it the real upload key before any release build leaves a developer machine;
  - **E10-R11 and every release build:** the flavor is chosen twice, as the Android product flavor and as the Dart entry point. `flutter build apk --flavor prod` without `-t lib/main_prod.dart` builds the `dev` entry point into a `prod`-flavored APK that talks to the local stack. Pair the two in one place (a script or a Make target), or let the Dart side read the Android flavor, before a staging or prod build is made;
  - **Renovate / E02-R07's pins:** `test` is 1.31.1 because Flutter 3.47.6's `flutter_test` pins `test_api` 0.7.12; move it back to the current `test` when the pinned Flutter allows. The APK build adds about 3.5 minutes to every `apps-mobile` CI run, and `sqlite3` 3.x builds SQLite through a native-assets hook that needs a C compiler on the runner (present on `ubuntu-24.04`);
  - **E15 (INV-04's lint rule):** the scaffold initialises `timezone` once and tests a `TZDateTime` across the 2026-10-25 change, but nothing yet stops zoned arithmetic on a plain `DateTime` in `apps/mobile`; the lint half of INV-04's automated check is still to build;
  - **E10-R03 (the offline cache):** `lib/src/db/database.dart`'s `CachedCalendars` table only proves the Drift toolchain; replace it with the real schema rather than migrating from it.
