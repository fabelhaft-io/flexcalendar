- **From the E05-R10 review 1, for later requirements:**
  - **E05-R03, E05-R04 (the first routes that can throw):** use the model as built. A route answers a CalDAV refusal with `sendCalDavProblem(reply, error, { instance: request.id })` and reaches CalDAV through `adapter.forUser(userId, { requestId: request.id })`; it never forwards a CalDAV body. The generic error handler is the only thing between an exception message and a response body, and mutation P5 of review 1 (the message copied into `property`) survives, because no test sends a hostile exception through it. The first route test that does (a route that throws `new Error(<canary>)` → a 500 problem, and the canary in neither body nor log) kills it;
  - **whoever next edits `classifyCalDavError` or `Service.php`:** two more survivors, both defence in depth. P9: the `PROPERTY_NAME` re-check in `server/api/src/problem.mjs` duplicates the adapter's filter and no unit case passes a `cf:name` that fails it (a lowercase or spaced name must give no `property` member). Q3: no `ServiceTest` case pins that `dav_failure` is logged for status 500 and above only; a 404, 412 or the guard's 403 must log nothing from `Service::run`;
  - **E08:** the problem `type` URIs are `https://flexcalendar.de/problems/<slug>` and nothing serves them. RFC 9457 says a `type` URI should resolve to documentation. Serve one page per slug (a static directory behind Caddy) or switch to URNs before a client switches on them. Production sets `CALFLEX_LOG_LEVEL` (default `info`: one line per response) and keeps `CALFLEX_TRUSTED_PROXY_HOPS=1` fixed; the CalDAV access line (`caldav request <METHOD> <status> <id>`) is one line per request, so size the log rotation for it;
  - **E05-R03:** Fastify answers `404` for a known path with another method (`POST /me`), so the `method-not-allowed` problem and the spec's `405` are declared but never sent. Make `405` real (with `Allow`) or drop it from the table and the spec; and declare the `X-Request-Id` response header per operation if a generated client should expose it (it is described in the spec's text only);
  - **E10-R02:** the generated Dart client has `Problem` where it had `Error` (`apps/mobile/lib/api/models/problem.dart`); a client branches on `type`, not on `title` or the status line, and reads `instance` as `urn:uuid:<correlation id>` for support requests.
