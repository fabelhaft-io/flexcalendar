- **From the E05-R05 review, for later requirements:**
  - **E05-R06, E05-R07 (the module and `recurrenceId`):** `src/occurrences.mjs` is the one expander; reuse it for plans instead of expanding again. The `recurrenceId` an occurrence carries is the instance's original start in the form the stored object spells it (`{date}`, `{utc}` or `{local, tzid, utc}`) and `null` for an event that does not recur; send exactly that back in an intent. `ical.js` iterates floating wall clocks only and every instant comes from `src/zones.mjs`; the RFC 5545 § 3.3.10 reading is one constant, `KEEP_NONEXISTENT_INSTANCES`, and its `true` is the owner's ruling of 2026-10-12 (`docs/02` § Recurrence);
  - **Phase 4 (Shared mode, stock-app objects):** a `DURATION` instead of `DTEND` reads as a zero-length instance (DAVx⁵ writes `DURATION` on recurring events), so nominal days/weeks plus an exact time part per RFC 5545 § 3.8.2.5 are still to do; an object with only override `VEVENT`s takes the first as its master and answers one non-recurring instance; `RECURRENCE-ID;RANGE=THISANDFUTURE` is read as one instance, not as a change of every later one; one object `ical.js` cannot parse is a `502` for the whole window, where it should be an `unsupported` entry with its own reason;
  - **E03-R12 (the recurrence bound, owner's ruling of 2026-10-12):** `sabre/vobject` stops after 3,500 instances, on a `calendar-query` with a `time-range` and on every `PUT` of a long finite series; R12 raises the bound to 50,000 and makes the write a `403`. The occurrences endpoint lists the collection without a `time-range` for the same reason, and need not change once R12 lands;
  - **E07-R01 (owner's ruling of 2026-10-12: not before M1):** the read lists the whole collection and expands every object on each request (cost O(events) in bytes and O(instances before the window) in CPU, bounded by 50,000 instances per object). A per-calendar cache keyed by the sync token (E05-R08) or a `prop-filter` for recurring objects is the next step; do not paginate the answer without telling the clients (a slice cannot be told from the whole). Build it with E07-R01, whose `CalendarChanged{calendarId, syncToken}` is the invalidation, because from Phase 4 every ping sends each member's devices back to this endpoint; sooner only if staging measures the endpoint's p95 above 500 ms;
  - **whoever next edits `expandObject` in `src/occurrences.mjs` (the cost guard):** an instance whose wall clock is more than two days plus the event's own length before the window is skipped without zone work; a unit test for the length term is missing (a guard that ignores the length passes every unit test and fails the oracle on 65 of 4,800 objects: a daily series of 3-day events with a window in the middle). Add the case when this file is next touched;
  - **E10-R02, E09 (the clients):** `unsupported[].href` is the CalDAV path of the object, which names the owner's principal; a client needs the `uid` only, so drop `href` from the answer when the contract is next revised;
  - **E15-R03 (corpus):** unbounded rules and window edges are covered by `test/occurrences.test.mjs`, not by corpus files, because the PHP runner and its 25 to 40 fixture bound are `server/caldav`'s; add them to the shared corpus when that suite is next edited.
