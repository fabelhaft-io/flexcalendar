# Implementation loop — queue and follow-ups

The state of the orchestrator loop (`.agents/skills/orchestrate/`): what runs next, the review findings that belong to a later requirement, and the questions waiting for the owner. Update it on the requirement branch whenever a review changes it. The epic Status cells and the PR list stay the source of truth for what is Done.

## Follow-ups waiting for their requirement

One file per source in [`follow-ups/`](follow-ups/): `from-<ID>.md` holds what that requirement's review found for later ones, `epic-<E>.md` and the topic files the rest. A requirement's PASS adds its own file on its branch, a new path that conflicts with nothing. **Only the reconcile `doc:` PR edits an existing line**: it removes what a merge resolved and deletes a file once it is empty. `make next-ready` counts the lines in all of them that name a requirement.

## Open with the owner

- **Free-text values on Private calendars (E03-R09 review 2).** The allow-list is of names, parameters and components, plus the fixed values of the table. The values of allowed properties are not inspected, so `UID:Chemo with Dr Smith`, a `TZID` parameter with a clinic's name, `PRODID` and `X-LIC-LOCATION` are all stored in cleartext. The README says so. A server-side backstop for `UID` is possible: INV-03 says our code creates UUIDv4 UIDs and ADR 0001 says no stock app ever edits a Private calendar, so the guard could require a UUIDv4 `UID` on Private. That is a change to E03-R09's table, hence an ADR 0001 amendment. Not started; say if you want it. A second reason came with E03-R10: a `PUT` body without `UID` is given `sabre-vobject-<uuid>` by SabreDAV's repair, which is not a UUIDv4 either.
- **A recurrence instance at a nonexistent local time: RFC 5545 § 3.3.10 says two things (E15-R02 review 1).** Its first paragraph says such an instance "MUST be ignored and MUST NOT be counted as part of the recurrence set"; its last says the time of an instance whose computed local start time does not exist, or occurs more than once, "is interpreted in the same manner as an explicit DATE-TIME value" (§ 3.3.5: the offset before the gap, so the instance is kept and counted). A daily 02:30 Berlin series has no instance on 2026-03-29 under the first reading and one at `20260329T013000Z` (03:30 local) under the second. The engines disagree with each other: `sabre/vobject` 4.6.1 (it answers a stock app's `calendar-query`) keeps and counts it at 01:30Z, `ical.js` 2.2.1 (the API's authority) keeps and counts it at 00:30Z, the offset after the gap. `spec/ical-fixtures/dst/cases.json` marks its eight `daily-skipped` cases `ruling: pending` and holds both answers. **Recommendation: the second reading** (keep, at the offset before the gap, counted): it is what `vobject` computes, and what a stock app most likely shows, so a Shared calendar's event is not missing from our own clients on one day a year. I have not tested a stock app. The E15-R02 implementer recommends the first reading instead (the RFC's explicit `MUST`, and no instant is invented for a time that never existed). It needs your ruling, as a line in `docs/02` § Recurrence or an ADR, before they count green: E05-R05 shipped the second reading as one constant (`KEEP_NONEXISTENT_INSTANCES` in `src/occurrences.mjs`), its runner reports the eight cases as `todo` and says which reading matched, and E12-R01's vectors wait for the ruling too; the invalid-date case (29 February) is unaffected and stays "ignored" (E15-R03's ruling).
