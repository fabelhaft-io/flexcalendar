## Brief for run 1

### What is already true

- `server/api/src/app.mjs` builds the Fastify app with `logger: false`. Its error handler answers `{"error":"rate_limited"}` for 429 and `{"error":"request_failed"}` otherwise; `server/api/src/auth.mjs` answers `{"error":"unauthorized"}` and other fixed `{error}` bodies; `spec/openapi.yaml` declares them as schema `Error` with `application/json`, and declares no `429` and no 5xx anywhere (`GET /me` can answer 500 `{"error":"internal_error"}` when the database fails).
- Rate limiting runs as one instance `onRequest` hook ahead of the bearer hook, so it counts a request before the token is verified. `GET /healthz` is exempt.
- The adapter (`server/api/src/caldav/adapter.mjs`) is the only module that reaches CalDAV. Its `CalDavError` carries `kind`, `status` and, for a `403` with a `DAV:error`, the `cf:` element names only (`cf:private-skeleton-only` with `cf:name`'s text, `cf:unmapped-collection`). It does no logging.
- The CalDAV service logs through PHP's `error_log` in two places: `server/caldav/internal/index.php` (`caldav delegation_error` / `caldav delegation_denied <reason>`, then 401) and `Service::run` in `server/caldav/src/Service.php` (`caldav dav_failure` for **every** exception, 404 and 412 and the guard's 403 included). Neither line has a correlation ID.
- `make test-caldav` already scans `compose logs caldav` for `CALFLEX_(REJECTED_HEADER|REJECTED_BODY|EVENT_CONTENT)_CANARY|CALFLEX_GUARD_MARKER` after the suite (see the `Makefile`). `make test-api-caldav` runs `server/api/test/integration/*.test.mjs` in the `api-test` compose service, which has no published port to the API.
- Spec: `docs/epics/E05-api-core.md` § E05-R10, RFC 9457, `docs/06` INV-01 and INV-07 ("no event content in logs, error messages or commit messages").

### What to build

1. **One problem+json model** for every error the API sends (`Content-Type: application/problem+json`), in one module that owns the table of problem types:
   - members: `type` (a stable URI reference per kind; your choice of scheme, documented in `server/api/README.md`), `title` (a fixed string per type), `status`, and `instance` = `urn:uuid:<the request's correlation ID>`. No `detail` unless it is fixed text. **Nothing in a body is derived from the request or from an exception message**: no path, no query value, no header, no validation message (Fastify's validation and JSON-parse errors echo values), no `pg` message (a unique violation prints the e-mail address).
   - It covers: the bearer hook's refusals, the 409/403/502/503 of `GET /me`, the rate limiter's 429 (keep `Retry-After`), Fastify's own 400/404/405/413/415 and validation errors (`setNotFoundHandler`, `setErrorHandler`, schema-validation errors), and any unhandled error as a 500. Whatever happens, the answer is a problem body and never Fastify's default JSON.
   - A function mapping the adapter's `CalDavError` to a problem (`unauthorized`, `403` with `cf:private-skeleton-only` → a type plus an extension member naming the offending property only if the adapter already filtered it, `cf:unmapped-collection`, `412`, `404`, `410`, others → 502/500). E05-R03 and E05-R04 will call it; it must never forward a CalDAV body. Unit-test it for every kind and with a hostile body.
2. **Correlation ID.** UUIDv4 per request (INV-03: `crypto.randomUUID()`), set with Fastify's `genReqId`. **Do not trust an inbound `X-Request-Id`** (`requestIdHeader: false`): accept it only when it is exactly a lowercase v4 UUID, otherwise replace it (log injection). Return it as `X-Request-Id` on **every** response, the 401s and 429s that never reach a route included. The adapter sends it to CalDAV as `X-Request-Id` on every call (a per-call option on the `forUser(...)` methods, or on `forUser` itself: your design, but E05-R03 must be able to pass `request.id` with one argument). The header is not part of the delegation signature.
3. **Request logging.** One structured line per request when the response is sent, from fixed fields only: correlation ID, method, the **route template** (`request.routeOptions.url`, or `unmatched`), status, duration in ms. Not the URL, query string, headers (the `Authorization` header above all), body, client address, token claims, e-mail, handle or `users.id`. Disable Fastify's default request/response serializers and `req` logging. Errors are logged by error name and, for `pg`, the SQLSTATE `code`, **never** `message` or `stack`. Use Fastify's built-in logger (pino comes with it; add no dependency). The level comes from `CALFLEX_LOG_LEVEL` (default `info`; invalid values stop the service at startup, like the other settings in `config.mjs`). `server/api/src/server.mjs`'s startup lines stay as they are.
4. **CalDAV side** (`server/caldav/`):
   - read `HTTP_X_REQUEST_ID`; use it only when it is a v4 UUID, else `-`; one `error_log` line per request on the internal listener with method (from a fixed allow-list, else `OTHER`), final status and the ID; **no path, no query, no header values**. The delegation-denied and `delegation_error` lines carry the ID too.
   - `dav_failure` is logged only for status 500 and above (the access line already carries the rest; 66 lines in one test run was noise). Keep `Service::errorResponse`'s "preconditions only" body.
   - Hardening from E03-R08's review: a `REPORT` with an empty or malformed XML body is a 500; SabreDAV's `Sabre\Xml\ParseException` is not a DAV exception. `Service::errorResponse` should answer `400` for that exception class and nothing else (a PHPUnit case with a malformed and an empty body through the real service; a mutation that widens it to every `\Throwable` must fail a test).
5. **Spec.** `spec/openapi.yaml`: replace schema `Error` by a `Problem` schema with `application/problem+json`, declare `429` (with a `Retry-After` header) and `500` on `GET /me`, and keep every code the route can answer. `GET /healthz` stays as it is. The contract test (`server/api/test/contract.test.mjs`) compares response codes, security and tags; extend it to compare response **content types** and to fail when a handler answers a code or type the spec does not declare. Do not edit the generated clients (`apps/mobile/lib/api`, `packages/api-client-ts`): the sandbox cannot regenerate the Dart one, and I do both in a separate commit.
6. **Settings** (every new variable is documented): `infra/dev/compose.yaml` passes `CALFLEX_LOG_LEVEL`, `CALFLEX_RATE_LIMIT_MAX` and `CALFLEX_RATE_LIMIT_WINDOW_SECONDS` to the `api` service as `${NAME:-default}`, and `infra/dev/.env.example` lists them with the defaults. `CALFLEX_TRUSTED_PROXY_HOPS` stays fixed at `"1"` in the Compose file (`infra/dev/check-stack.mjs` checks it; keep that check) and `.env.example` says so in a comment. Update `server/api/README.md`'s settings table.
7. **Tests.**
   - Unit and in-process (`buildApp` with a log stream captured through `logger: { stream }`): a canary in the path, the query string, a header, the `Authorization` token, a JSON body, a body that is not JSON, an oversized body and an unknown route; afterwards **no log line and no response body contains the canary**; the ID is on every response, an inbound non-UUID `X-Request-Id` is replaced and a v4 one kept; every error body validates against the spec's `Problem` schema; `GET /me` with a failing store answers a 500 problem and logs the error name only; a `pg`-style error whose message holds an e-mail address does not reach the log. Include the missing rate-limit case from E05-R01's review 3 (mutants `R4` and `R5` survived): at one trusted hop, a forged first `X-Forwarded-For` entry does not choose the bucket (the key is the last entry).
   - In the stack (`server/api/test/integration/`, run by `make test-api-caldav`): the marker values go **through the adapter** into CalDAV — a content property (`SUMMARY`) on a Private calendar, and bytes standing in for an envelope — and the guard's `403` becomes the problem from item 1 with the element names and no value; the request ID you pass appears in the CalDAV log. Extend `make test-api-caldav` the way `make test-caldav` does: after the suite, scan `compose logs api caldav` for the markers (new ones, `CALFLEX_`-prefixed like the existing canaries, and add them to the `test-caldav` pattern if you reuse it) and fail on a hit. Show that the scan itself fails when a marker is planted in a log line.
