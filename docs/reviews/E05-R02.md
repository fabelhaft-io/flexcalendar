## Brief for run 1

### What is already true

- `CALFLEX_CALDAV_ORIGIN: http://caldav-internal:8081` and `CALFLEX_DELEGATION_KEYS` are already on the compose `api` service (E03-R01); the epic's "moves to the internal listener" is done.
- The signing format is E03-R01's: `X-Calflex-Principal: v=1; k=<key-id>; p=<users.id>; t=<unix-seconds>; n=<nonce>; s=<signature>`, `n` = 16 random bytes base64url without padding, `s` = base64url (no padding) of `HMAC-SHA256(key, "calflex-delegation-v1\n" + METHOD + "\n" + request-target + "\n" + p + "\n" + t + "\n" + n)`, `request-target` = the path and query **exactly as sent**. `CALFLEX_DELEGATION_KEYS` is a comma-separated `<key-id>:<base64 key>` list, each key at least 32 bytes; the signer uses the **first**. Reference implementation: `server/caldav/src/Delegation.php`; vectors: `server/caldav/tests/Fixtures/delegation-vectors.json` (the first has a plain path; one has `?a=1&b=%2F`; one an encoded space).
- The service verifies the signature over the raw `REQUEST_URI` and records each nonce once; an unauthenticated failure is one `401` for every reason. A rejected write is `403` with a `DAV:error` document holding `cf:private-skeleton-only` (and a child `cf:name`) or `cf:unmapped-collection`; the adapter must carry those element names and nothing else out (no body text, no value).
- The internal listener has no published port: it is reachable only from the `delegation` network, so **API tests that talk to it must run inside the stack**, like `make test-caldav` does. The host cannot reach `172.30.91.2`.

### What to build (`server/api/`, plus the files below)

1. **`server/api/src/caldav/adapter.mjs`**: the only module that imports `tsdav` or knows `X-Calflex-Principal`, the origin variable or the keys. `createCalDavAdapter({ origin, keys, fetch, now, nonce })` returns `forUser(userId)`, whose methods are the small surface E05-R03, R04 and R08 need: `makeCalendar(calendarId)` (`MKCALENDAR`), `putObject(calendarId, name, ics, { ifMatch, ifNoneMatch })`, `getObject`, `deleteObject(…, { ifMatch })`, `listObjects(calendarId, { start, end })` (a `calendar-query` time-range) and `syncChanges(calendarId, token)` (`sync-collection`). `userId` and `calendarId` must be UUID-shaped (reject anything else before a request is made: they go into a path). Hrefs are `/calendars/<userId>/<calendarId>/…`.
   - **Signing happens per request**, so it cannot sit in tsdav's static `headers` or `authFunction`: pass tsdav the per-call `fetch` it accepts (I read `fetch?: typeof globalThis.fetch` on `davRequest` in tsdav 2.4.0; verify it on each function you use, and use raw `fetch` where a function lacks it or a report is missing). The wrapper signs the **URL it actually sends**: build the `URL`, take `pathname + search` from that same object, sign, and send that object. Fresh nonce and `t = floor(now/1000)` per request, the first key, no retries of a signed request.
   - `redirect: 'manual'` (a redirect is an error), `AbortSignal.timeout(10_000)`, a 4 MiB response cap. No logging at all.
   - Errors: a `CalDavError` with `status` and, when the body is a `DAV:error`, a list of the precondition element names (`cf:private-skeleton-only`, `cf:name`'s text only if it matches `[A-Z][A-Z0-9-]{0,63}`); **never the body, a header value or the URL**. A `401` is one error kind (`unauthorized`) whatever the reason; a database outage on the service also looks like a 401, which the adapter cannot tell apart (the service log can).
   - Keys: parse once at creation, fail on an empty list, a missing separator, a non-base64 key, a key under 32 bytes or a duplicate id (the service does the same); keep them out of every error message. The pure signing function is exported for the tests.
2. **The lint rule**: `eslint.config.mjs` (repository root) gets a `no-restricted-imports` (static and dynamic `import('tsdav')`) for `tsdav` everywhere except the adapter file, and a test (`ESLint`'s `Linter` or its CLI on a temp file) shows an import outside it **fails with that rule** and the adapter passes. Also a test that no other file under `server/api/src/` mentions `X-Calflex-Principal`, `CALFLEX_CALDAV_ORIGIN` or `CALFLEX_DELEGATION_KEYS`.
3. **Unit tests** (no containers): every vector of `delegation-vectors.json` (read the file from `server/caldav/tests/Fixtures/`; do not copy it) reproduces `s` and the whole header; odd targets (`?`, `%2F`, an encoded space, unicode, `..`) are signed as `URL` serializes them; a rotated key list signs with the first; nonces differ and are 22 base64url characters; invalid key lists fail; every non-2xx status maps to the right error; a `DAV:error` body yields element names only; a hostile body never appears in the error; redirects and oversize responses fail.
4. **Integration tests inside the stack** (`server/api/test/integration/*.test.mjs`): a new compose service `api-test` (profile `test`, networks `stack` and `delegation`, `mem_limit`, `depends_on` `caldav` healthy, the database URL as `calflex_api`, the origin and the keys), built from `server/api/Dockerfile` with a new `test` target that adds `server/api/test/` and the vectors file, running `node --test test/integration/*.test.mjs`. Make target `test-api-caldav` (`migrate`, then `run --build --rm -T api-test`), registered as `infra/scripts/verify/invariants/E05-R02.json` and described in that registry's README; `.dockerignore` lets the new paths through (it is an allow-list); `infra/dev/check-stack.mjs` knows the new service (the "only these join `delegation`" check lists `api,caldav,caldav-test`; add `api-test`, keep every other check, and show each check still fails on its own mutation); `infra/dev/README.md` lists the target.
   Cases: two users, each with a `users` row, a `calendars` row and an `owner` `calendar_members` row (created by the test through `calflex_api` and removed after), each creates their own Private calendar through the adapter, writes a valid skeleton (`X-CALFLEX-ENVELOPE-SHA256`, no content properties; `server/caldav/tests/GuardCases.php` shows one) and reads it back **as themselves**; user B asking for user A's href gets `404`; `If-None-Match: *` on an existing object and a stale `If-Match` give `412`; a content property gives `403` with `cf:private-skeleton-only` and the property's name and nothing else; `listObjects` and `syncChanges` return what was written; a bad key id or a tampered signature is the one `401`. Clean up through the adapter (`DELETE`) and the database; the suite passes twice in a row.
