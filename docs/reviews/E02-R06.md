# Review — E02-R06 · CI pipeline

- **Brief before run 1** (2026-10-05). Nothing has been implemented yet. These are the follow-ups that earlier reviews assigned to E02-R06 (`docs/reviews/follow-ups.md`), plus the reviewer's constraints. Treat each one as a fix request.
- Branch: `feat/E02-R06-ci-pipeline`.

## Brief

The requirement is in `docs/epics/E02-repo-tooling-ci.md` § E02-R06: GitHub Actions runs `make verify` on every PR, with path filters per component, cached dependencies and a required status check on `main`.

You can't run GitHub Actions in the sandbox. Write the workflow, check it statically (see 6), and list for the reviewer what to observe on a real PR. The reviewer pushes the branch and watches the runs.

## Fix requests

1. **Read the pins, never repeat them:**
   - `actions/setup-node` with `node-version-file: .nvmrc`;
   - pnpm through corepack from `package.json#packageManager`;
   - `subosito/flutter-action` with `flutter-version-file: apps/mobile/.fvmrc`;
   - `shivammathur/setup-php` with PHP 8.4, the version `server/caldav/composer.json` pins;
   - `actions/setup-java` with JDK 21 (`apps/mobile/android/gradle/gradle-daemon-jvm.properties`) and `gradle/actions/setup-gradle`.
   JDK 21 isn't auto-provisioned: the daemon JVM criteria have no toolchain download URLs, so CI must install it.
2. **Pin every third-party action by its full commit SHA**, with the version tag in a trailing comment. Check each SHA against the action's release.
3. **Path filters that work with a required check.** A workflow-level `paths:` filter leaves a required check "pending" forever on PRs it skips. Use:
   - one workflow that always runs;
   - a change-detection job that decides which components ran (`server/api`, `server/caldav`, `apps/mobile`, `apps/web`, `packages/*`, and the cross-cutting files: root manifests, `Makefile`, `infra/`, `.github/`);
   - component jobs gated with `if:`;
   - one final aggregate job, which is the check to make required, that fails if any job it needs failed or was cancelled.
   A change to cross-cutting files runs everything. A PR touching only `apps/web` runs the web checks plus the cross-cutting ones (the Accept line). Every job runs the component's `make verify-<component>`; the full `make verify` runs whenever cross-cutting files change. Never duplicate the verify recipe in YAML.
4. **Cache dependencies:** the pnpm store, Composer's cache, pub, and Gradle (through `setup-gradle`).
5. **Install, then verify:** CI runs `corepack pnpm install --frozen-lockfile` and `composer install` in `server/caldav`. It starts the local stack (`make dev`) before the stack-dependent suites, because `make verify` deliberately doesn't start it (E02-R04). On the runner, use Podman as on dev machines (`02`). If rootless Podman can't run there, say so and make the stack step use the Makefile's `PODMAN_COMPOSE` override, documented in a comment.
6. **Pin-consistency check**, a new script under `infra/scripts/` with a unit test, run by the tooling component's `test`:
   - `.nvmrc` agrees with `package.json`'s `devEngines.runtime.version` and its `engines.node` range;
   - both pubspecs' Dart SDK constraint (`apps/mobile`, `packages/crypto_dart`) admits the Dart version that the `.fvmrc` Flutter release ships. Take that version from Flutter's `releases_linux.json` (`dart_sdk_version`) as a pinned fixture in the repo, not from the network at check time.
   Add a bad fixture that fails each comparison.
7. **Check the workflow statically in the sandbox:** run `actionlint`, downloaded with its checksum checked, and list the result.
8. **The required status check is a repo setting.** Don't try to set it. Name the aggregate job in `openQuestions`, so the owner can make it required.

Change nothing else.
