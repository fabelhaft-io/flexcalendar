Before it kills the process, `KillingCalendars` queries **its own connection, inside the open transaction**, for what that transaction sees and prints one line, which `OutboxWriter` flushes and the parent asserts: the object's presence (and its etag, so that an update is told from the old bytes), the number of `sabredav.calendarchanges` rows for the calendar, and the number of `public.caldav_changes` rows for the collection. For create the object is present and the outbox row is not yet; for update the etag already differs; for delete the object is already gone. The parent then asserts the usual state from a **second** connection (nothing persisted). A seam moved before the write, with or without the transaction, must now fail create, update **and** delete: re-run V1, V2 and V3 yourself by hand-editing, and list what you saw.

## Brief (condensed)

One transaction per object write: `BEGIN`, `SELECT synctoken … FOR UPDATE` on the SabreDAV calendar row (serializing writers), the E03-R09 guard first, the parent write, a protected no-op seam, the outbox insert, `COMMIT`; any throwable rolls back. Decision pinned with the owner (2026-10-10): `sync_token` is the number `sync-collection` reports for the change, `calendarchanges.synctoken + 1`. A collection with no `public.calendars` row is refused up front with a 403 precondition, never a 500. The kill test runs the guarded backend in a child process and SIGKILLs it in the seam.
