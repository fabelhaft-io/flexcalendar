## Brief for run 1

### What is there

`src/GuardedCalendars.php` (E03-R09) subclasses `Sabre\CalDAV\Backend\PDO` and overrides `createCalendarObject` and `updateCalendarObject` after the write guard; `uri($calendarId)` maps SabreDAV's `[calendarId, instanceId]` to the collection URI, which is `public.calendars.id`. `deleteCalendarObject` is not overridden. `COPY` and `MOVE` reach these methods too (a `MOVE` is a create in one calendar and a delete in another, two transactions). `calflex_caldav` has DML on `public.caldav_changes` (`id` default, `calendar_id` FK to `public.calendars` with `ON DELETE CASCADE`, `sync_token bigint`, `uid text`, `change_type` in `created|updated|deleted`) and on the `sabredav` tables. `make test-caldav` runs `tests/Integration` in the one-off `caldav-test` service (registered in `infra/scripts/verify/invariants/E03-R01.json`); no new service, network, variable or dependency is needed.

### What SabreDAV does (read in sabre/dav 4.7.1 at `f36f002`, not run: write tests that fail if I am wrong)

- `createCalendarObject`, `updateCalendarObject` and `deleteCalendarObject` each run statements in autocommit: the object, then `addChange()`, which inserts into `sabredav.calendarchanges` the **current** `calendars.synctoken` N (`INSERT … SELECT synctoken`), then `UPDATE calendars SET synctoken = synctoken + 1`. No transaction anywhere.
- `sync-collection` reports `http://sabre.io/ns/sync/<token>` where the token is the last change's `synctoken + 1`, i.e. N + 1 after one change.
- Two concurrent writes can both read N before either updates, and then record the same N. Serialize them (below).

### Decision pinned here: which number is `sync_token`

E03-R10 says both "the sync token SabreDAV assigned to the change" (N, what `calendarchanges.synctoken` holds) and, in its Accept line, "the token that `sync-collection` reports for the change" (N + 1). **Use the Accept line: `sync_token` is the numeric part of the token the collection reports after the change, N + 1**; E05-R08 and E07 hand that number to clients as "changed up to". Prove it in the test by running `sync-collection` and comparing, and list the choice in the PR as a decision for the owner.

### Design

- Each of the three methods runs in **one transaction** on the service's connection: `BEGIN`; `SELECT synctoken FROM sabredav.calendars WHERE id = ? FOR UPDATE` (this serializes writers per calendar, so tokens cannot repeat); the guard check (E03-R09 stays first in effect: a rejected write changes nothing); the parent method (object, `calendarchanges` row, token increment); read the UID and the new `synctoken`; `INSERT INTO public.caldav_changes (calendar_id, sync_token, uid, change_type)`; `COMMIT`. Any throwable rolls back and is rethrown unchanged. `Delegation::accept` has already committed by then; if a transaction is open anyway, fail the write instead of nesting.
- UID: for `created` and `updated` read it from `sabredav.calendarobjects` after the write; for `deleted` read it **before** the delete. `calendar_id` is the collection UUID. The outbox holds the UID and nothing else from the object (INV-01: no event content).
- A collection with **no `public.calendars` row** (or a non-UUID URI) cannot take objects now, because the FK would fail. Refuse the write explicitly, before any statement, with a DAV error that is a 4xx (`Forbidden`, 403, is fine; say what you chose) and the usual preconditions-only body. Never skip the outbox row and never answer 500. Tests that PUT into a collection must create its `public.calendars` row first (`GuardTest` and `ServiceTest` already do; check `testCopyAndCrossCollectionMoveCannotBypass`).
- The failure seam for the test is a **protected no-op method** called between the parent write and the outbox insert (name it `afterObjectWrite` or similar). It is overridden only by a subclass under `tests/`. No environment variable, header, configuration or function in `src/` may make the service kill itself, and the runtime image must not contain test code (it copies `src`, `public`, `internal` and the `Caddyfile` only).

### Tests (`tests/Integration/OutboxTest.php`, a new file)

1. Over the delegation header on a Private calendar: a `PUT` creates one `created` row; a second `PUT` with `If-Match` one `updated` row; a `DELETE` one `deleted` row. Each has the right `calendar_id` and `uid`, and `sync_token` equals the number in the `sync-collection` report taken right after that change (the report with the previous token lists the object).
2. **The Accept test.** A child `php` process (`proc_open`) runs the guarded backend against the test database as `calflex_caldav` with the subclass whose `afterObjectWrite` kills the process with SIGKILL (`posix_kill(getmypid(), SIGKILL)`, or `exec('kill -9 ' . getmypid())` if `posix` is missing; the official PHP images have `posix`). The parent asserts the child died of the signal, then asserts in the database that there is **no** `calendarobjects` row, **no** `calendarchanges` row, an unchanged `calendars.synctoken` and **no** `caldav_changes` row; and that the same child without the kill leaves all four. Do it for create, update (the old object bytes and etag unchanged) and delete (the object still there).
3. Concurrency: two writers on one calendar at once (`curl_multi` or two child processes) produce distinct, increasing `sync_token`s, each equal to its `calendarchanges.synctoken + 1`. If the test image cannot do this, say so in `openQuestions`.
4. A write into a collection with no `public.calendars` row answers a 4xx and leaves no object, no change and no outbox row.
5. Clean up what you create (deleting the `public.calendars` row cascades the outbox rows); `public.users`, `public.calendars`, `public.delegation_nonces`, `public.caldav_changes` and the `sabredav` tables must be empty after the suite, and the suite must pass twice in a row.
