**V8 survives.** Moving the `COMMIT` ahead of the outbox insert (create) passes: the seam sits before the commit, so the kill happens before either write is committed, and the normal path writes both. A crash between a too-early commit and the outbox insert would lose the row, and no test sees that window. It needs a second seam after the insert, killed there: with the correct order nothing persists, with commit-then-insert the object does. The implementer's own list of mutations for me named this one and said the tests would fail; they do not. I recorded it in `follow-ups.md` for whoever next touches `GuardedCalendars` (E03-R02 and E03-R08 do, but only through other methods), and the owner can ask for a fourth run.

The kill test now proves where it kills: the writer prints `SEAM {object, etag, changes, outbox, transaction}` from its own open transaction before the SIGKILL, and the parent asserts it (create: the object is there and the outbox row is not; update: the etag already differs; delete: the object is gone), and then asserts from a second connection that nothing persisted.

Scope and invariants: `server/caldav/` and this doc. INV-01/03/05/07/12: the outbox holds the collection UUID, the `UID`, the change type and the number, no event content; no ID generator; no crypto; the writer prints counts and an etag, not content.
