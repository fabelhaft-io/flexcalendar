## Brief before run 1

### What to build

1. **Dependencies**, exact pins, in `dependencies` of `server/api` (the production image migrates from the API image): `node-pg-migrate` 9.0.0 and `pg` 8.23.1. `corepack pnpm --filter @calendar-flex/api add node-pg-migrate@9.0.0 pg@8.23.1` (`saveExact` is on). If you cannot produce `pnpm-lock.yaml`, say so in `openQuestions`; the reviewer generates it in a separate `chore(E04-R01)` commit. `@types/pg` is an optional peer: add it as a devDependency only if the typecheck needs it.
2. **The chain** in `server/api/migrations/`, named `<unix-ms>_<slug>.mjs` (or `.sql` with `-- Up Migration` and `-- Down Migration`). Use the real millisecond timestamp of the day, not a made-up number: the tool fails a run when a migration is older than one already applied, which is the property we want.
3. **The vendored SabreDAV scripts** outside `migrations/` (for example `server/api/sabredav/`), byte for byte, plus a JSON record: package, tag `4.7.1`, commit, source URL, and the SHA-256 per file. The two migrations read the hash from the record and refuse to run when the file differs. No Prettier, ESLint or any formatter may touch these files.
4. **`make migrate`** (idempotent) and a small `make migrate-down` (one step back). `make migrate` starts only Postgres (`$(COMPOSE) up --detach --wait postgres`), then runs a one-off `migrate` service (compose profile `migrate`, built from `server/api/Dockerfile`, like `seed`). The Dockerfile must copy `migrations/` and the vendored directory into the image, **and `.dockerignore` (writable) is an allowlist**: add `!server/api/migrations` and the vendored directory next to the API's entries, or the build fails with "no such file".
5. **The stack move to PostgreSQL 18**: `postgres:18-alpine`, the volume mounted at `/var/lib/postgresql`, `infra/dev/README.md`'s table row, and the stale `postgres:17-alpine` claims. `CONTRIBUTING.md` gets `make migrate`, the new Podman prerequisite below, and a sentence that a volume created by 17 needs `make dev-reset`.
6. **`CALFLEX_MIGRATE_DATABASE_URL`**: optional override in `infra/dev/.env.example`, defaulting in compose to the bootstrap login (`caldav`) on `postgres:5432/${CALFLEX_POSTGRES_DB}`. E04-R02 switches it to `calflex_migrate`. Never print the URL; the CLI doesn't.

### Facts checked upstream on 2026-10-08, so you need not

- `node-pg-migrate` 9.0.0 (published 2026-07-17): Node `>=20.11`, peer `pg >=4.3 <9`, deps `glob ~13.0.0`, `jiti ~2.7.0`, `yargs ~18.0.0`, MIT, ESM, no install scripts. `pg` 8.23.1 is `latest`. `INV-07` passes with both added (run on a scratch copy of `main`).
- The CLI is `node-pg-migrate [up|down|create|redo] [name] [options]`. Options you need: `--database-url-var`, `--migrations-dir`, `--check-order` (default on), `--single-transaction` (default on), `--schema`, `--lock`, `--verbose` (default on: it prints every statement, noisy for the SabreDAV script). `.sql`, `.js`, `.cjs` and `.mjs` load; a subdirectory of `migrations/` is ignored.
- Behaviour I ran on postgres 18.6 against a fresh database. Your tests must expect it: the first `up` creates; the second prints `No migrations to run!` and exits 0; `down N` reverses N migrations in reverse order and `down 0` reverses all; `export const down = false` makes `down` fail with `Error: User has disabled down migration on file: <name>` (exit 1) and the `pgmigrations` row stays; a failing statement rolls back the **whole run** (an earlier new migration's table is gone too, `pgmigrations` unchanged, exit 1); a migration older than the latest applied one fails with `Not run migration <a> is preceding already run migration <b>` (exit 1).
- **The SabreDAV scripts run unmodified in their own schema.** A run is one transaction, so the search path must be transaction-local and put back, or the next migration would land in `sabredav`. This worked with the pristine `calendars` script:

  ```js
  export const up = (pgm) => {
    // verify the file's SHA-256 against the record first
    pgm.createSchema('sabredav');
    pgm.sql("SELECT set_config('search_path', 'sabredav', true)");
    pgm.sql(script);
    pgm.sql("SELECT set_config('search_path', 'public', true)");
  };
  export const down = (pgm) => {
    pgm.dropSchema('sabredav', { cascade: true });
  };
  ```

  `calendars` runs first. `propertystorage` comes after it, uses the same `set_config` pair without `createSchema`, and its down drops only its table. Document in the migration that the first down destroys all CalDAV data: the dev and test chain uses it, production never does (its rollback is a restore, E08-R04). Do not re-express the DDL with the `pgm.createTable` DSL.
- **The scripts**, tag `4.7.1`, commit `f36f002dce082e1d425c4a0dc8c71a6b176c3b07`, at `https://raw.githubusercontent.com/sabre-io/dav/4.7.1/examples/sql/<file>` (hashes re-checked today, sizes 3117 and 329 bytes):

  | File | SHA-256 |
  |---|---|
  | `pgsql.calendars.sql` | `871609815dd8f642cb7909f736a70efa396b8b2144b10f8d458a3624048c2496` |
  | `pgsql.propertystorage.sql` | `bf0f3445f47c1ae0d647ad29d4c8edb41366687a55dfb3ad92ed2fd8bf96db3c` |

  Download and check the hashes. If the sandbox can't reach GitHub, write everything else and say so; the reviewer commits the two files after checking them. Together they create 7 tables, all `SERIAL` keys: `calendarobjects`, `calendars`, `calendarinstances`, `calendarsubscriptions`, `calendarchanges`, `schedulingobjects`, `propertystorage`. **Never import** `pgsql.principals.sql` or `pgsql.users.sql`: each inserts a default `admin` account. Composer's package leaves out `examples/`, which is why the record exists (E03-R01 compares `composer.lock` with it).
- **`postgres:18-alpine`** is 18.6, `PGDATA=/var/lib/postgresql/18/docker`, `VOLUME /var/lib/postgresql`. A volume made by 17 does not migrate silently: the container exits 1 with `Error: in 18+, these Docker images are configured to store database data in a format which is compatible with "pg_ctlcluster"…`. That is the loud failure we want; the fix is `make dev-reset`.
- **Zitadel v4.16.0 `start-from-init` runs on 18**: two of three first starts on a scratch copy came up healthy (two of two on 17). The failed one was a race in the image entrypoint: its temporary server listens on the Unix socket only and logs "ready to accept connections" about 3 s before the real server listens on TCP. The compose healthcheck (`pg_isready` over the socket) goes green in that window, Zitadel dials TCP, gets "connection refused" and exits 1, and `up --wait` fails. Measured: the socket probe succeeded 2.8 s before `pg_isready --host 127.0.0.1` did. **You are authorised to change the healthcheck to probe `127.0.0.1`** (one flag). Without it the CI stack action, which starts from an empty volume every run, is flaky. Keep the shell form of the check.
- The CI runner's Podman is 4.9.3, a dev host's 6.1.3. Use fully qualified image names when calling `podman run` yourself (`docker.io/library/postgres:18-alpine`).

### Registering the check in `make verify`

`make verify` doesn't start the stack, and neither does the component job in CI. So the check is a **component test in `server/api`**, picked up by the existing `node --test test/*.test.mjs`, not an invariants or corpus JSON entry (those expect a running stack). **Two files**, so the sandbox can run one:

- `test/migrate-record.test.mjs`, **no database**: reading the record; the hash comparison, with one changed byte; the file layout (exactly the two scripts, none of the forbidden two); every file in `migrations/` exports `down` or `down = false` with a comment; the Makefile target names. The sandbox runs this one.
- `test/migrate.test.mjs`, **database-backed**. It starts its **own** throwaway Postgres:
  - `podman run --rm -d -p 127.0.0.1::5432 …` with the image **read from `infra/dev/compose.yaml`** (the `postgres` service), so there is one source for the version. Read the port back with `podman port`. A fresh database per case (`CREATE DATABASE`), the container stopped in `after`.
  - Readiness: retry a real client connection over TCP until a deadline. Do not use the socket-based `pg_isready` (the race above).
  - If `podman` is missing the test **fails** with a message naming it. It does not skip: a skipped gate is vacuous. `CONTRIBUTING.md` lists Podman as a prerequisite of `make verify` from now on.
  - Cases: (a) a fresh database after `up` has exactly the seven tables in `sabredav` and `public.pgmigrations`, nothing else; (b) a second `up` changes nothing (row count and table list); (c) `down` to zero removes the schema, leaves only `pgmigrations`, and `up` again restores it; (d) the vendored directory copied to a temp dir with one byte changed makes `up` fail, with no schema and no `pgmigrations` row; (e) a temp migrations directory with `down = false` refuses `down`; (f) a good migration followed by a broken one leaves nothing behind. Fixtures (d)–(f) are built by the test in a temp directory. A deliberately broken migration must never sit in `migrations/`.
