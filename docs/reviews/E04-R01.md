## Brief before run 1 (condensed)

Decided by the owner on 2026-10-08 (PR #36): `node-pg-migrate` 9.0.0 on `pg` 8.23.1; only SabreDAV's `pgsql.calendars.sql` and `pgsql.propertystorage.sql`, from the `sabre/dav` 4.7.1 tag (commit `f36f002dce082e1d425c4a0dc8c71a6b176c3b07`), into the schema `sabredav`, byte for byte, with a record of tag, commit and SHA-256. **Never import** `pgsql.principals.sql` or `pgsql.users.sql`: each inserts a default `admin` account.

- Behaviour of the tool on postgres 18.6: second `up` prints `No migrations to run!`; `down N` reverses in reverse order, `down 0` all; `down = false` makes `down` fail (`User has disabled down migration on file: <name>`, exit 1); a failing statement rolls the **whole run** back (exit 1); an older migration fails with `Not run migration <a> is preceding already run migration <b>`.
- The scripts run unmodified: a run is one transaction, so the search path is set transaction-locally (`set_config(…, true)`) and put back to `public` afterwards. The first down destroys all CalDAV data: dev and test only, production rolls back by restore (E08-R04).
- A volume made by 17 makes the 18 container exit 1 (the fix is `make dev-reset`). The Podman prerequisite of `make verify` is documented in `CONTRIBUTING.md`; the DB test fails, never skips, without it.
- Not for this requirement: API tables, roles, a `depends_on` on migrations (E04-R02, E03-R01). "From the first production deploy on, CI migrates a copy of the last released schema" waits for E08 (`follow-ups.md`).
