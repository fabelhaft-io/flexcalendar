- **Negative control:** `GuardPlugin` unregistered in `Service.php` → `Tests: 39, Failures: 1`, only `testUidBackstopRefusalsAndAcceptedShapes` (the mixed-`UID` rows fall back to SabreDAV's `415`). So the plugin is what makes mixed `UID`s a `403`, **and** it is what turns every update into a `500`.

### Finding: the cause

`GuardPlugin::beforeWriteContent` reads the stored object with `$node->get()` and passes it to `PrivateSkeleton::storedUid(string $text)`. Sabre's `IFile::get()` "may either return a string or a readable stream resource" (`vendor/sabre/dav/lib/DAV/IFile.php:46`), and `CalendarObject::get()` returns the backend's `calendardata` as it came out of PDO, which for Postgres `bytea` is a **stream**. Under `declare(strict_types=1)` that is a `TypeError`, which `Service::run` answers with `500`. `tests/Unit/GuardPluginTest.php` passes because its fake node's `get()` returns a string.

### Fix requests

1. Read the stored `UID` in the hook without assuming a string. Either use the store's `uid` column, as `GuardedCalendars::objectUid` does for the backend check (preferred: one source for the stored `UID`, no re-parse), or turn a resource into a string with `stream_get_contents` before parsing. Keep `strict_types`.
2. `GuardPluginTest`: add a node whose `get()` returns a stream (`fopen('php://memory', 'r+')` with the bytes written and rewound), and show that an update keeping the `UID` passes and one changing it is refused.
3. Run what the sandbox can, and list `make test-caldav` (twice) and `make test-api-caldav` for the reviewer; every update case above must pass there.

Change nothing else.

### Where the code is today (`main` at `ffb58f7`)

- `GuardedCalendars::createCalendarObject` and `updateCalendarObject` call `WriteGuard::calendar($uri, $calendarData)`, which runs `PrivateSkeleton::calendar` (the E03-R09 allow-list, names only) on a Private calendar and turns a `SkeletonViolation` into `PrivateSkeletonOnly` (`403`, `cf:private-skeleton-only`, the offending name in `cf:name`). Create and update are already separate backend calls, so "a create is a `PUT` to a name the collection does not hold" maps onto `createCalendarObject`; check that SabreDAV never routes a new name through `updateCalendarObject` or the reverse.
- Since E03-R12 (PR #91) both methods end in `throw MaxInstances::translate($exception);` after the rollback. Leave that line and its place alone: the bound must stay a `403` `CALDAV:max-instances` on every mode, and your refusals belong inside the Private guard (`docs/reviews/follow-ups/from-E03-R12.md`).
- `GuardedCalendars::objectUid` already reads the stored `UID` of an object (the outbox uses it); an update that changes the `UID` compares against that.

### Facts to establish, not assume

- **SabreDAV's repair.** `sabre/vobject` gives a `VEVENT` without `UID` the value `sabre-vobject-<uuid>` (`vendor/sabre/vobject/lib/Component/VEvent.php:82`), and `Sabre\CalDAV\Plugin::validateICalendar` may repair the body before the backend sees it. Find out whether the guard sees the body before or after the repair, and make a `PUT` without `UID` a refusal either way (the epic says so); the test must send a body with no `UID` line, not one with `sabre-vobject-…`.
- **Same `UID` across `VEVENT`s.** Check whether SabreDAV's own validation already refuses mixed `UID`s and with which status. The epic wants our `403` with the precondition either way, so the guard must check it itself and run where SabreDAV's check cannot answer first with something else; if SabreDAV answers first with a `4xx` of its own, say so and show which.
- **The object name.** The request URI's last segment, as the backend receives it (`$objectUri`), must equal `<uid>.ics` exactly, lowercase, on create.
