# Review — E03-R11 · UID backstop on Private calendars

## Brief for run 1

The requirement is in `docs/epics/E03-caldav-service.md` § E03-R11; the ruling behind it is ADR 0001 § Amendments, "Owner's ruling (2026-10-12)", and the skeleton paragraph it amends. Executor `agent+review`: the owner approves the PR before merge. Writable paths: `server/caldav/` only. No API change, no migration, no dependency.

### Where the code is today (`main` at `ffb58f7`)

- `GuardedCalendars::createCalendarObject` and `updateCalendarObject` call `WriteGuard::calendar($uri, $calendarData)`, which runs `PrivateSkeleton::calendar` (the E03-R09 allow-list, names only) on a Private calendar and turns a `SkeletonViolation` into `PrivateSkeletonOnly` (`403`, `cf:private-skeleton-only`, the offending name in `cf:name`). Create and update are already separate backend calls, so "a create is a `PUT` to a name the collection does not hold" maps onto `createCalendarObject`; check that SabreDAV never routes a new name through `updateCalendarObject` or the reverse.
- Since E03-R12 (PR #91) both methods end in `throw MaxInstances::translate($exception);` after the rollback. Leave that line and its place alone: the bound must stay a `403` `CALDAV:max-instances` on every mode, and your refusals belong inside the Private guard (`docs/reviews/follow-ups/from-E03-R12.md`).
- `GuardedCalendars::objectUid` already reads the stored `UID` of an object (the outbox uses it); an update that changes the `UID` compares against that.

### Facts to establish, not assume

- **SabreDAV's repair.** `sabre/vobject` gives a `VEVENT` without `UID` the value `sabre-vobject-<uuid>` (`vendor/sabre/vobject/lib/Component/VEvent.php:82`), and `Sabre\CalDAV\Plugin::validateICalendar` may repair the body before the backend sees it. Find out whether the guard sees the body before or after the repair, and make a `PUT` without `UID` a refusal either way (the epic says so); the test must send a body with no `UID` line, not one with `sabre-vobject-…`.
- **Same `UID` across `VEVENT`s.** Check whether SabreDAV's own validation already refuses mixed `UID`s and with which status. The epic wants our `403` with the precondition either way, so the guard must check it itself and run where SabreDAV's check cannot answer first with something else; if SabreDAV answers first with a `4xx` of its own, say so and show which.
- **The object name.** The request URI's last segment, as the backend receives it (`$objectUri`), must equal `<uid>.ics` exactly, lowercase, on create.

### What to build

1. The checks of the epic, on a Private calendar only, with the same `PrivateSkeletonOnly` `403`: on **create**, every `VEVENT` and `VALARM` `UID` a lowercase UUIDv4 (the epic's regex, anchored with `\A…\z`), all `VEVENT`s one `UID`, the object name `<uid>.ics`; a `PUT` without a `UID`, create or update; an **update** that changes the stored `UID`; an `RRULE` with an `X-` rule part, on create and update. The rejection names `UID`, the object name (choose one fixed token, e.g. `OBJECT-NAME`, and document it) or `RRULE`, never the value.
2. An update of an object whose stored `UID` is not a UUIDv4 is accepted (Phase 4's mode switch keeps stock-app `UID`s, INV-03). Seed such an object directly in the store for the test, since `mode` accepts only `private` until Phase 4.
3. `PRODID`, `TZID`, `X-LIC-LOCATION`, `TZNAME` and `TZURL` stay unchecked.
4. Keep `server/caldav/README.md` true, and make `tests/GuardCases.php` (or a sibling) the table the new test reads, beside E03-R09's.

### Tests the epic asks for

- A table-driven test beside E03-R09's (`tests/Unit/GuardTest.php`, `tests/Integration/GuardTest.php`) that refuses each case with the precondition and accepts: a lowercase UUIDv4 create, and an update that keeps a non-UUID `UID` stored while the calendar was not Private.
- E03-R09's marker test extended: a marker placed in a refused `UID`, object name or `X-` rule part appears in no response body and no log line (`make test-caldav` scans the service log for `CALFLEX_GUARD_MARKER`; use that marker or another name the `CALFLEX_LOG_CANARIES` pattern in the root `Makefile` already matches, since the `Makefile` is not yours to edit).
- The API's create path against the live stack (`make test-api-caldav`) must still pass: its `randomUUID()` and `<uid>.ics` meet the rule. That is the reviewer's run; don't change `server/api/`.

### What the sandbox can't run

Podman and the stack. Write the integration tests, run the unit suite, PHPStan (`-d memory_limit=1G` if the sandbox's 128M limit crashes its workers) and php-cs-fixer, and list the stack commands for the reviewer in `openQuestions`.
