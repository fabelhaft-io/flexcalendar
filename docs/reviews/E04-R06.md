## Brief for run 1

Two deliverables, both in E04-R06's Accept line: a schema test and a check script.

### 1. The schema test (`server/api/test/schema.test.mjs`)

An assertion over the live schema, not a list of table names. Extend the existing case that counts the `id` columns (9 of them, all `uuid` with `gen_random_uuid()`); do not weaken it.

- In the schema `public`, every column that has a default and is `uuid`-typed has exactly `gen_random_uuid()`; no column anywhere in `public` is an identity column or defaults to `nextval(…)`.
- **Exempt, by name**: the whole schema `sabredav` (SabreDAV's tables use `SERIAL` keys and the upstream scripts are not ours to change; the integers never reach an href, the collection URI is `calendarinstances.uri`, which holds the API's UUID) and the table `public.pgmigrations` (node-pg-migrate's own `SERIAL` id).
- `event_envelopes`, `user_keys`, `user_key_wraps` and `calendar_keys` have composite natural keys and **no generated id**. The check must not ask for one.
- Write the check as a function that returns the offenders, and test it both ways. The negative controls exist on PostgreSQL 18 (checked on `postgres:18-alpine`, 18.6): `ALTER TABLE public.<table> ADD COLUMN x uuid DEFAULT uuidv7()` reads back in `information_schema.columns.column_default` as `uuidv7()`; `serial` reads back as `nextval('<table>_<column>_seq'::regclass)`; and `GENERATED ALWAYS AS IDENTITY` has a **NULL** `column_default` and `is_identity = 'YES'`, so the check must look at `is_identity` too. Each must come back as an offender in a fresh database, and `sabredav.*` and `public.pgmigrations` must not.
- **Do not assume your work is the newest migration** (`down 1`): E04-R03's, E04-R04's and E04-R05's tests broke or had to be written around that. This requirement adds no migration; keep it so, and make no case depend on how many migrations exist.

Follow all of it; read `invariants.mjs` and its test first.
