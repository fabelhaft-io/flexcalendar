# Review — E08-R10 · Zitadel database role: evaluation

## Brief for run 1

The requirement is in `docs/epics/E08-operations.md` § E08-R10. **Nothing is implemented**: the local stack (`infra/dev/compose.yaml`, `infra/dev/postgres/initdb/`, `infra/zitadel/`) stays exactly as it is. The deliverable is an ADR with status `Proposed` and the measurement harness that produces its numbers. Writable paths: `docs/adr/` and `infra/dev/zitadel-role-eval/`.

### What to deliver

1. **`docs/adr/0005-zitadel-database-role.md`**, from `docs/adr/0000-template.md`, status `Proposed`: the context (the epic's first paragraph, D-17, D-11, D-19, ADR 0004's single host), the three options of the epic at least, each criterion of the epic per option, a recommendation, and the consequences for E08-R11, E08-R02 and E08-R08. Every measured claim cites the command and its output. Where a measurement has not run yet, the cell says `pending — reviewer runs <script>` and nothing is claimed.
2. **The harness**, `infra/dev/zitadel-role-eval/`: one script per option (bash, `set -euo pipefail`), each runnable by the reviewer with one command, using rootless `podman compose` with **its own compose file and project name** (`calflex-zre-<option>`), its own volume and **no published host port that the default stack uses** (8443, 5432, 8080, 3000 must stay free; publish nothing unless a step needs it). Each script:
   - starts Postgres 18 (`postgres:18-alpine`, as the stack) and Zitadel at the pinned `v4.16.0` from an empty volume, with that option's role setup (for the pre-provisioned option, an initdb SQL file inside the harness, written like `infra/dev/postgres/initdb/20-roles.sql`);
   - prints, with the command echoed before its output, the privilege checks the epic lists: `\du`, `has_database_privilege` for the role on every database, and attempts as Zitadel's runtime role to read the `caldav` database (create one in the harness to stand in for it), `CREATE ROLE` and `CREATE DATABASE`;
   - checks whether admin credentials remain in the Zitadel container's environment or files (`podman exec … env`, names only, values masked; never print a password);
   - has a `--starts N` mode that repeats the first start from an empty volume N times (default 10) and records each outcome and its time to healthy (Zitadel's `/debug/healthz` or `/debug/ready`, whatever v4.16.0 serves: check it);
   - has an `--upgrade` mode that runs `setup` (or the start command) of the newest v4 release against the database the pinned version created, **as the same runtime role**. The newest release on 2026-10-12 is `v4.19.4` (GitHub releases, published 2026-10-01); check that the image tag exists on `ghcr.io/zitadel/zitadel` before relying on it;
   - removes its own project with `podman compose -p calflex-zre-<option> down -v` at the end, and never touches `flexcalendar-dev`.
   A `README.md` there lists the scripts, what each prints and how long a run takes.
3. The production shape and the secrets questions of the epic are answered in prose in the ADR, from the docs (`02` § Hosting and § Backups, D-11's OpenTofu state schema `calflex_tofu`, D-19), the Zitadel documentation for v4.16.0 (the `init` help text the epic quotes, `start-from-init`, `start-from-setup`, `setup`), and the measurements.

### Facts to establish, not assume

- Whether `zitadel init` passes without `CREATEROLE`, and whether `start-from-setup` works against a database and role that the bootstrap created: find out by running them in the harness design, not from the docs alone.
- Which role `zitadel-config` (E02-R09, OpenTofu with the PG backend, `PG_CONN_STR` in `infra/dev/compose.yaml`) needs for `calflex_tofu`, and whether it can be a role of its own.
