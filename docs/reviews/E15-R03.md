## Brief for run 1

### What is already true

- `make verify-corpus` runs `infra/scripts/verify.mjs corpus`, which executes every `*.json` file under `infra/scripts/verify/corpus/` (a nonempty array of command argument arrays, run from the repository root, in filename order, exit nonzero on failure). The directory holds only a README, and `spec/ical-fixtures/` only a README: this is the first corpus content. `make verify` runs `verify-corpus` last, after every component gate.
- Engines in the repository: `ical.js` 2.2.1 in `server/api` (the recurrence authority, `docs/02` § Recurrence) and `sabre/vobject` 4.6.1 in `server/caldav` (via SabreDAV 4.7.1; it answers `calendar-query` time-range filters and computes each object's first and last occurrence, `docs/05` risk 2, second paragraph). 5.0.0 of `sabre/vobject` exists upstream, but SabreDAV 4.7.1 requires `^4.5`: do not bump it. `server/api/src/recurrence-key.mjs` already uses `ical.js` for recurrence identity; `server/caldav/tests/Fixtures/Europe-Berlin.ics` is an existing `VTIMEZONE`.
- `ical.js` ships no zone data: a `TZID` resolves only through a `VTIMEZONE` in the same document or the global registry (and must not be registered globally from a client's document). `sabre/vobject` resolves a `TZID` through PHP's own zone database. That difference is part of what the corpus must show.
- INV-02 (round-trip preserves every property and parameter) belongs to E15-R01; this requirement is only about recurrence expansion.

### What to build

1. **The corpus**, `spec/ical-fixtures/rrule/`: one `.ics` per case, one `VEVENT` master (plus overrides where the case is about overrides). Name the source of each case in `spec/ical-fixtures/rrule/README.md`: a table of fixture, what it exercises, and the source (an RFC 5545 section and example, or the `docs/05` example). At least the cases the epic names: `BYSETPOS`; ordinal `BYDAY` (`1MO`, `-1FR`, `2TU`); `BYMONTHDAY=-1`; `UNTIL` in UTC against a zoned `DTSTART` (one that falls on the local day boundary of Europe/Berlin and one across a DST change); `COUNT` with `EXDATE`; the `docs/05` example "every second Tuesday except in months with a fifth Wednesday" (write the closest honest `RRULE`, say in the README how you read it, and keep the case even if the engines agree); overrides with `RECURRENCE-ID` (moved, and cancelled through `EXDATE`). Add the RFC 5545 § 3.8.5.3 examples that fit (weekly with `WKST`, monthly on the last weekday, `BYSETPOS=-2`, yearly `BYWEEKNO`, leap-day yearly, `INTERVAL` across the 29th/30th/31st: where the RFC says an occurrence is skipped). Every fixture has `DTSTART` with `TZID` and a `VTIMEZONE`, or `Z`, or `VALUE=DATE` (INV-04); all UIDs are UUIDv4. Aim for 25 to 40 cases, not hundreds.
2. **One window.** A fixed absolute 5-year window, `2026-01-01T00:00:00Z` up to `2031-01-01T00:00:00Z`, never `now`. An engine's output for a fixture is a sorted list of occurrences: for a timed event the UTC instant of each start (`YYYYMMDDTHHMMSSZ`), for an all-day event the date, plus the `RECURRENCE-ID` key of an override it replaced. Write the normalisation once per engine and say in the README what it drops (durations, which instance an override is).
3. **Two runners, each inside its own component's test suite** so a dependency bump in either is caught by that component's gate: `server/api/test/` (a `*.test.mjs` run by `npm test`) and `server/caldav/tests/` (a PHPUnit test in `tests/Unit/`, which `composer test` runs, plus a small CLI script in `tests/` that prints the normalised JSON; `lint` and `phpstan` cover `tests/`, not `bin/`). Each suite (a) expands every fixture, (b) asserts the result against a **golden expectation written beside the fixture** wherever the source gives one (the RFC examples list their results; the others you derive by hand and say so), and (c) writes its normalised output as JSON to a path given by an environment variable when set, for the comparison below. Nothing reads the wall clock; the suites pass twice in a row.
4. **The comparison** `make verify-corpus` runs, registered as `infra/scripts/verify/corpus/E15-R03.json` (extend the README there): a script `infra/scripts/corpus-compare.mjs` with `infra/scripts/corpus-compare.test.mjs` beside it (top level of `infra/scripts/`, because the tooling gate runs `infra/scripts/*.test.mjs` and type-checks `infra/scripts/*.mjs` only; Prettier and ESLint cover the tree; build synthetic outputs inline or in a temp directory) that runs both runners, diffs the two outputs per fixture, and fails with the fixture, the first differing occurrence, and each engine's value. **Resolution is a ruling, not a skip:** `spec/ical-fixtures/RULINGS.md` holds one entry per accepted disagreement in a fixed, parseable shape (fixture id, the two outputs' first difference, the RFC 5545 section, and which engine is right); the script reads it. A disagreement without a ruling fails; a ruling whose fixture no longer disagrees also fails (a stale ruling hides the next regression); a malformed ruling fails. If the engines disagree on a fixture, **do not change the fixture to make them agree**: write the ruling, and if one engine is wrong in a way that matters for the product (`vobject` decides what a stock app's date-range query sees; `ical.js` is the authority), say so in the entry (`docs/05` risk 2: the fix is to correct the stored first and last occurrence or patch upstream, never fork).
5. **Prove the gate bites.** Tests of the script with synthetic outputs for: equal outputs, a difference, a difference with a ruling, a stale ruling, a malformed ruling, a missing fixture in one engine's output (a gate over an empty input cannot fail: it must fail when an engine returns zero fixtures, or fewer than the corpus holds), an engine that crashes. And a negative control on each real engine: a deliberately wrong expansion (an off-by-one `BYSETPOS`, say) in a **copy** of a fixture makes the golden check fail in that component's suite — describe how you ran it in `summary`; do not commit the broken copy.
