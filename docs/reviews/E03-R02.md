## Brief for run 1

### What is there

- **Internal listener** (`internal/index.php` → `Service::create`): the tree root is SabreDAV's own root collection holding `principals/` and `calendars/`. The DAVACL plugin answers `{DAV:}current-user-principal` for any path (E03-R01's `ServiceTest` already checks it on one PROPFIND); the CalDAV plugin answers `{urn:ietf:params:xml:ns:caldav}calendar-home-set` and DAVACL `{DAV:}principal-URL` on a principal node. Nothing is tested for those two yet, and `Principals` (read-only, acting user only) is ours.
- **Public listener** (`public/index.php`): standalone, no autoloader, no database, never reads `X-Calflex-Principal`; `GET /healthz` is `200 ok`, everything else is `401 Unauthorized`. `PublicTest` runs the real entry in a fresh PHP process and asserts no output on stderr.
- SabreDAV 4.7.1 has **no** `/.well-known/caldav` handling (I grepped `lib/`): the redirect is ours.

### What to build

1. **The redirect, on the public listener only.** The exact path `/.well-known/caldav` (a query string is ignored and never reflected) answers **`301` with `Location: /`**, for every method (`GET`, `HEAD`, `OPTIONS`, `PROPFIND`; stock apps start with a `PROPFIND`), a fixed body or none, `Cache-Control: no-store` kept, no `Server` header, **without reading any header**: a valid delegation header, a malformed one and none give byte-identical responses, and nothing is logged. The target is the constant `/`: never derived from `Host`, a forwarded header or the request (no open redirect, no host-header injection). Everything near it stays `401`: `/.well-known/caldav/`, `/.well-known/CALDAV`, `/.well-known/caldavx`, `/.well-known/carddav`, `//.well-known/caldav`, `/x/.well-known/caldav`. Put the match in one small function that `PublicTest` can call.
2. **Discovery on the internal listener** is E03-R01 code; do not change `Service` unless a case below fails because of a defect. Add the integration case from the Accept: with a delegated principal, `PROPFIND /` (Depth 0) → `current-user-principal` = `/principals/<users.id>/`; `PROPFIND` of that principal → `principal-URL` = the same href and `calendar-home-set` = `/calendars/<users.id>/`; `PROPFIND` of the home at Depth 1 lists a Private calendar made in the test at `/calendars/<users.id>/<calendars.id>/`. Parse the multistatus (`DOMDocument`, namespaces), assert the exact `href` text, and show the case **fails against a wrong value** (hand-edit the expected string, run, restore, and say so in `openQuestions`). Another user's principal or home still answers 404, identical to an id that exists nowhere (E03-R01 follows; keep it).
3. **No cardinality of stock-app behaviour is asserted here**: Apple Calendar, DAVx⁵ and the others are checked on staging by E15-R05. Do not add `Sharing`, scheduling or `carddav` anything.
