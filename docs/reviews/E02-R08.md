### Fix requests

1. **"Work is sliced into requirements, one per epic" is wrong.** An epic holds many requirements (E02 has R01–R08). Write that each epic in `docs/epics/` is split into requirements named `E<nn>-R<nn>`.
2. **Say who opens and who merges a PR.** The doc says the harness never pushes, opens a PR or merges, but not who does. In this project:
   - the reviewer records the findings in `docs/reviews/<ID>.md` on the branch;
   - a BLOCKED verdict goes back to the implementer on the same branch, for at most two fix cycles;
   - after a PASS, the reviewer pushes the branch and opens the PR;
   - **only a human merges**, and `agent+review` PRs additionally need human approval (rule 7).

   Add this in two or three sentences under Branch naming.
3. **Don't cite INV-01/INV-07 for "no event content in commit messages".** INV-01 is about the API keeping no event fields that diverge from the `VEVENT`. INV-07 is about the server never decrypting. Neither covers commit messages. Keep the rule, and give its real source: the "no event content in logs" rule in `agent-team/src/prompts/guardrails.md` and E05-R10. Or state it without a citation.
4. **Remove the `Refs: <ID>` footer** from the example and the footer list. No commit uses it, nothing reads it, and the subject already carries the ID. Keep `Co-Authored-By`. Also make the review-commit example match the history: `E<nn>-R<nn>: review <n> (<VERDICT>)`, for example `E02-R02: review 1 (BLOCKED)`, not `review 1 findings (BLOCKED)`.
5. **Don't hard-code the next ADR number.** "with 0001–0004 taken, the next one is `0005`" goes stale with the next ADR. Write "the next free number in `docs/adr/`".

Change nothing else. Re-run markdownlint and your verbatim check.
