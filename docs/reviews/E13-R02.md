# Review — E13-R02 · Sidecar API

## Brief for run 1

The requirement is in `docs/epics/E13-private-mode.md` § E13-R02. The spec: ADR 0001 § Private calendars — cryptography (the sidecar table, change detection and its write order, D-06, D-07), `spec/crypto.md` (accepted 2026-10-12: §1.1 the header and the 64 KiB ceiling, §5.1 `X-CALFLEX-ENVELOPE-SHA256`, §5.2 the canonical `recurrence_id`), and the table `public.event_envelopes` (E04-R04, migration `1791643469785_event-envelopes.mjs`). Writable paths: `server/api/` and `spec/openapi.yaml`. This branch is **stacked on E03-R11** (`feat/E03-R11-uid-backstop-on-private-calendars`, PR #99, waiting for the owner), whose CalDAV `UID` rules your writes meet.

### What to build

1. **Read endpoints** for envelopes in bulk: by calendar, by a `uid` list, and by delta (the E05-R08 change feed's token), declared in `spec/openapi.yaml` first. A member who may read the calendar may read its envelopes; anyone else gets the 404 an unknown calendar gets.
2. **Write**: store an envelope opaquely in `event_envelopes` with its SHA-256 (D-06), and commit it with the skeleton in D-06's order: insert the envelope row, then `PUT` the skeleton carrying `X-CALFLEX-ENVELOPE-SHA256` with `If-Match`, then garbage-collect the superseded row. A crash between the steps leaves the previous version readable; orphan rows (an envelope no skeleton names) are removed after 24 h. The API checks **only** the header (version, epoch ≤ 2,147,483,647), the size (≤ 65,536 bytes, `spec/crypto.md` §1.1, which settles the follow-up asking for a server-side ceiling) and that the hash agrees with the skeleton. It never opens an envelope (INV-07).
3. **The client chooses the `UID` of a Private create.** E03-R11's epic note says E13-R02 and E10-R06 are "where a client starts choosing the `UID` (the envelope's AAD binds it, and an offline create needs it before reconnecting)", and ADR 0001 (amended 2026-10-12) has the server require a lowercase UUIDv4 `UID` on create. So E05-R04's Private create takes a client-chosen `uid`, validated by the API exactly as E03-R11 does (lowercase UUIDv4 `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`, a `422` before CalDAV is asked), stored as `<uid>.ics`; a Shared create keeps minting it. Declare it in `spec/openapi.yaml` first.

### Follow-ups that belong here

- **from-E05-R04:** a Private `PATCH` that moves `start` or `end` without a new `envelopeSha256` leaves an envelope whose AAD no longer matches. Refuse it with a `422` (the bound fields are `DTSTART`, the end and `RRULE`, `spec/crypto.md` §2.2), naming the member only.
- **from-E04-R04 and from-E12-R01:** `recurrenceKey` (`src/recurrence-key.mjs`) converts with `ical.js`, which gets RFC 5545 § 3.3.5 wrong on a skipped and on a repeated local time; `spec/crypto.md` §5.2 and §3.4 pin the offset before the gap and the first occurrence. Take the instant from `src/zones.mjs` (`instantOf`), never register a client's `VTIMEZONE` globally, and add the two Berlin cases of `spec/crypto-vectors/canonical-timing-v1.json` (`20260329T023000`, `20261025T023000`) to its test, read from the file.
- **from-E03-R11:** the in-process CalDAV double (`test/support/caldav-store.mjs`) mirrors E03-R11's rules; keep your tests passing through it.

### Tests

Unit tests through the real app with the double; a stack test (`test/integration/`) that commits envelope + skeleton against the live service, kills the write between the envelope row and the skeleton `PUT` (a failing double or an injected fault) and shows the old envelope still readable; the 24 h collector with an injected clock; canaries in envelope bytes that reach no log line (`make test-api-caldav` scans for them). No event content in logs, errors or commit messages.
