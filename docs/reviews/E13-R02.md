### Findings

1. **A Private create is two calls and the first one writes the skeleton** (your `openQuestions`: `POST /events` with `uid` and hash, then `PUT /envelopes/{uid}` with `If-Match`). A client that crashes or goes offline between them leaves a skeleton whose envelope never existed: the event shows on every member's device with no content, and nothing collects it. D-06's order is "insert the envelope row, then `PUT` the skeleton". It works for a create too, because the client now chooses the `UID`: the row is keyed `(calendar_id, uid, recurrence_id, envelope_sha256)` before any object exists, and an orphan row is collected after 24 h.
2. **`uid` is optional on a Private create.** Without it the API mints one, but a client cannot seal an envelope whose AAD binds a `UID` it doesn't know yet, so that create can never get valid content. The brief made the client choose it on Private.
3. The `changes.test.mjs` failure above.

### Fix requests

1. **One request commits a Private create in D-06's order**: `POST /calendars/{calendarId}/events` on a Private calendar carries the envelope (standard base64, the same checks as `PUT /envelopes/{uid}`: header, epoch, ≤ 65,536 bytes, its SHA-256 equal to `envelopeSha256`), the API inserts the row **first**, then `PUT`s the skeleton with `If-None-Match: *`; a failed `PUT` leaves only an orphan row for the 24 h collector, never a skeleton without its envelope. Declare it in `spec/openapi.yaml` first. Test the crash between the two steps on a create (an injected fault after the row insert: no object, the row collected later) as you did for the update.
2. **`uid` is required on a Private create** (`422` without it, the same validation as now); a Shared create keeps minting it. Update the tests that create Private events without one.
3. **`test/integration/changes.test.mjs`:** where it moves `start` on a Private event, send a new envelope and `envelopeSha256` (through the sidecar write, as a client would), so the case still proves "a create, an update and a delete between two tokens" against the new rule. Don't weaken what it asserts.

Change nothing else. The orphan sweep after each write, the `property` member naming `DTSTART`/`DTEND`, the `uid`/`since` `422` and the tombstone rule are fine as they are.

## Brief for run 1

The requirement is in `docs/epics/E13-private-mode.md` § E13-R02. The spec: ADR 0001 § Private calendars — cryptography (the sidecar table, change detection and its write order, D-06, D-07), `spec/crypto.md` (accepted 2026-10-12: §1.1 the header and the 64 KiB ceiling, §5.1 `X-CALFLEX-ENVELOPE-SHA256`, §5.2 the canonical `recurrence_id`), and the table `public.event_envelopes` (E04-R04, migration `1791643469785_event-envelopes.mjs`). Writable paths: `server/api/` and `spec/openapi.yaml`. This branch is **stacked on E03-R11** (`feat/E03-R11-uid-backstop-on-private-calendars`, PR #99, waiting for the owner), whose CalDAV `UID` rules your writes meet.

### What to build

1. **Read endpoints** for envelopes in bulk: by calendar, by a `uid` list, and by delta (the E05-R08 change feed's token), declared in `spec/openapi.yaml` first. A member who may read the calendar may read its envelopes; anyone else gets the 404 an unknown calendar gets.
2. **Write**: store an envelope opaquely in `event_envelopes` with its SHA-256 (D-06), and commit it with the skeleton in D-06's order: insert the envelope row, then `PUT` the skeleton carrying `X-CALFLEX-ENVELOPE-SHA256` with `If-Match`, then garbage-collect the superseded row. A crash between the steps leaves the previous version readable; orphan rows (an envelope no skeleton names) are removed after 24 h. The API checks **only** the header (version, epoch ≤ 2,147,483,647), the size (≤ 65,536 bytes, `spec/crypto.md` §1.1, which settles the follow-up asking for a server-side ceiling) and that the hash agrees with the skeleton. It never opens an envelope (INV-07).
3. **The client chooses the `UID` of a Private create.** E03-R11's epic note says E13-R02 and E10-R06 are "where a client starts choosing the `UID` (the envelope's AAD binds it, and an offline create needs it before reconnecting)", and ADR 0001 (amended 2026-10-12) has the server require a lowercase UUIDv4 `UID` on create. So E05-R04's Private create takes a client-chosen `uid`, validated by the API exactly as E03-R11 does (lowercase UUIDv4 `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`, a `422` before CalDAV is asked), stored as `<uid>.ics`; a Shared create keeps minting it. Declare it in `spec/openapi.yaml` first.
