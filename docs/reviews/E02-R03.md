### Fix requests

1. **The login UI's base path must answer.** The Caddyfile routes only `path /ui/v2/login/*` to `zitadel-login`. The login app redirects `/ui/v2/login/` to `/ui/v2/login`, which then goes to the core and returns 404, and that is exactly where `/` sends a developer. Route both `/ui/v2/login` and `/ui/v2/login/*` to `zitadel-login`.
   - Expected result: `curl -L https://auth.localhost:8443/` ends on a rendered login page (HTTP 200).
   - E08-R08 later requires a deploy check that `/ui/v2/login` answers, so the dev stack should behave the same way.
2. **`make seed` must work with any `CALFLEX_HTTPS_PORT`.** Inside the network, the seed calls `https://auth.<domain>:${CALFLEX_HTTPS_PORT}`, but Caddy's container always listens on 8443. With 9443 the seed waits for five minutes and fails with `ECONNREFUSED …:9443`.
   - Make the seed reach Zitadel independently of the published port, and keep TLS verification or explain why you drop it.
   - Zitadel resolves the instance from the request's host; check whether it also compares the port.
   - The reviewer will run `CALFLEX_HTTPS_PORT=9443 make dev && make seed` under a separate `COMPOSE_PROJECT_NAME`, and the default 8443 again.
3. **README facts** (`infra/dev/README.md`):
   - "run as uid 0 *inside* their containers, as upstream asks": cite where upstream asks for it, or state only the actual reason (the bootstrap PAT files in the shared volume). If `zitadel-login` only reads the volume, check whether it needs uid 0 at all.
   - "That seeding belongs to E04": no doc says so. E04 is the schema, and calendars are created through the API (E05-R03). Write "later requirements" instead.
