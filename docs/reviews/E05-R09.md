## Brief for run 1

### What is already true

- `src/ical-rmw.mjs` (E05-R04) builds and patches events with `Z` and `VALUE=DATE` times **only**; a write carrying a `TZID` is a 422. It reads and round-trips a stored `TZID` time or `VTIMEZONE` untouched and never converts one (`describe` reports `{local, tzid}`); `assertOrder` cannot compare a `Z` instant with a `TZID` wall clock, or two zones, and leaves them alone. It registers nothing in `ical.js`'s global `TimezoneService` and must keep not doing so: one client could redefine `Europe/Berlin` for everyone (E04-R04's note).
- **`ical.js` 2.2.1 has no zone database and is wrong on two single local times** (`spec/ical-fixtures/dst/README.md`, reproduced in review): a skipped local time gets the offset after the gap, a repeated one the second occurrence. RFC 5545 § 3.3.5 form 3 says the offset **before** the gap and the **first** occurrence. So no instant the API computes from a `TZID` may come from `ical.js`.
- `spec/ical-fixtures/dst/cases.json` (E15-R02) is the RFC's answer for 104 cases over six zones; `dst/README.md` explains the fields. The `daily-skipped` family carries `ruling: pending` and two answers: **do not make it pass or fail**, E05-R05 owns the runner and the owner owns the ruling.
- The write guard (E03-R09, `server/caldav/src/PrivateSkeleton.php`) allows in a `VTIMEZONE` only `TZID`, `LAST-MODIFIED`, `TZURL`, `X-LIC-LOCATION` and, inside `STANDARD`/`DAYLIGHT`, `DTSTART`, `TZOFFSETFROM`, `TZOFFSETTO`, `RRULE`, `RDATE`, `TZNAME`. A zone copied from tzurl.org carries `X-PROLEPTIC-TZNAME` and is refused. `spec/ical-fixtures/synthetic/microsoft-windows-zone-name.ics` carries `TZID=W. Europe Standard Time` with its own `VTIMEZONE`.
- No time-zone data source is pinned anywhere. Node 24's ICU (`Intl.DateTimeFormat` with `timeZone`) is what E15-R02's validator already uses as an oracle.
- Spec: `docs/epics/E05-api-core.md` § E05-R09; INV-02, INV-04; `docs/05` risk 2.

### What to build (choices marked **mine** are the orchestrator's; say in the handoff if you deviate)

1. **The zone source, mine: Node's ICU, no new dependency.** `src/zones.mjs`: `isIanaZone(name)` (the exact `Area/Location` or `UTC` spelling ICU knows: **case-sensitive**, so `europe/berlin` is refused; link names such as `Asia/Calcutta`, `US/Eastern` and `Asia/Kolkata` are valid IANA names and accepted; `W. Europe Standard Time`, `Mars/Olympus`, the empty string and anything with spaces or control characters are not); `instantOf(local, tzid)` implementing § 3.3.5 form 3 exactly (repeated → first occurrence, skipped → the offset before the gap) from ICU's offsets; `localOf(instant, tzid)`; and `vtimezoneFor(tzid, {from, to})`. Nothing is registered in `ical.js` globally.
2. **`vtimezoneFor`, mine:** a `VTIMEZONE` with `TZID` and `X-LIC-LOCATION`, and `STANDARD`/`DAYLIGHT` observances inside the guard's allow-list, built from ICU's real transitions as `RDATE`s (explicit transitions are valid and every client reads them). It must make every instant the object can have resolve to the same UTC as `instantOf` — for a recurring event with no end, through 2100. Document the size this gives for Europe/Berlin and say in the handoff if it worries you.
3. **Write path:** `start` and `end` accept `{local: "YYYYMMDDTHHMMSS", tzid}` besides `{utc}` and `{date}`; the object gets `DTSTART;TZID=…:local`, one embedded `VTIMEZONE` per `TZID` it uses, no `TZID` left without its `VTIMEZONE`. An unknown or Windows name, a floating `local` without `tzid`, and a `tzid` with `utc` or `date` are the fixed 422. `UNTIL` in a rule on a `TZID` start must be UTC (RFC 5545 § 3.3.10): extend the rule check, with a test.
4. **`assertOrder` compares everything**: `utc`, `date` and `local`+`tzid` against each other, through `instantOf`.
5. **INV-02 stays:** a `PATCH` that does not touch `start`/`end` keeps a Windows `TZID` and its own `VTIMEZONE` byte for byte (the corpus fixture). A `PATCH` that touches a time field of an object whose stored `TZID` the resolver cannot resolve is a 422 unless it replaces both `start` and `end` with values the API can write.
6. **`parsed`:** a `TZID` time reads as `{local, tzid, utc}` where the zone resolves (the DST-correct instant a client should show), and `{local, tzid}` where it does not. Update the spec and the schemas; the clients are regenerated by me.
7. **Tests:** `src/zones.mjs` against `cases.json`: every case of the kinds `skipped`, `repeated`, `control`, `view-zone` (with `expectedLocal`), `all-day` and `daily-existing` equals the resolver's answer, and the table is read from the file, never copied. Zone-name table (accepted and refused). `vtimezoneFor`: every transition of the six table zones for 2026 and 2027 resolves identically through the generated `VTIMEZONE` (parse it with `ical.js` in the test only) and through `instantOf`, **except** that `ical.js` is not the oracle for the two known-wrong single times: compare those to the table. The generated `VTIMEZONE` contains only allowed properties (test the allow-list as data). Route tests through the real app; the E15-R01 `checkRoundTrip` still holds over the whole corpus. In the stack (`make test-api-caldav`): a `TZID` event with its `VTIMEZONE` is **accepted by the live guard** (create, read back byte-identical, patch the end).
