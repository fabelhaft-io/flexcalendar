### What changed

`Calflex\RecurrenceBound` (a server plugin `Service::create` installs) sets `Settings::$maxRecurrences` to its one constant, 50,000, and serves `CALDAV:max-instances` on every `ICalendar` node. `Calflex\MaxInstances` is a `Forbidden` that serialises `<C:max-instances/>` in `urn:ietf:params:xml:ns:caldav`; `GuardedCalendars` translates the vendor's `MaxInstancesExceededException` into it after the rollback, on create and update, outside the Private guard. The API's `parsePreconditions` reports that one element as the fixed token `C:max-instances` (text and attributes unread), `classifyCalDavError` maps it to the new `too-many-instances` `422`, declared in `spec/openapi.yaml`'s create and patch `422` descriptions in the style of `window-too-large`. Both READMEs describe it.

### Facts checked upstream (2026-10-12, `sabre/vobject` 4.6.1 and `sabre/dav` 4.7.1 as locked)

- `Sabre\VObject\Settings::$maxRecurrences` is `3500` by default (`vendor/sabre/vobject/lib/Settings.php:54`). `Recur\EventIterator::next()` throws `Sabre\VObject\Recur\MaxInstancesExceededException` (a plain `\Exception`, not a DAV exception) once its counter passes the bound; `-1` disables it. The counter counts every instance walked, including those a `time-range` query fast-forwards past.
- SabreDAV's PDO backend computes `firstoccurence`/`lastoccurence` on every create and update (`getDenormalizedData`) by walking a **finite** series up to 2038; an infinite one is not walked. That walk is what turns a daily `COUNT=4000`, an `UNTIL` in 2040 or an hourly series over a year into today's `500`.
- `{urn:ietf:params:xml:ns:caldav}max-instances` is already in `Sabre\CalDAV\Plugin`'s protected properties (`Plugin.php:222`) but no `propFind` handler answers it, so the collection property is ours to serve (RFC 4791 § 5.2.8: a positive integer on the calendar collection).
- The precondition element of RFC 4791 § 5.3.2.1 is `<C:max-instances/>` in the CalDAV namespace (`urn:ietf:params:xml:ns:caldav`), **not** in our `cf:` namespace. The API adapter's `parsePreconditions` (`server/api/src/caldav/adapter.mjs`) reports only elements of `https://flexcalendar.de/ns/caldav` today, so it must learn to report this one element too, as narrowly as it reads the `cf:` ones (a fixed name, no text, no attributes forwarded).

### Design constraints

1. Set the bound **once**, where the service is configured (`server/caldav/src/Service.php::create` or the two front controllers' common path), never in `vendor/`. One named constant for 50,000.
2. Turn `MaxInstancesExceededException` into a `Sabre\DAV\Exception` subclass of ours that answers `403` and serialises `<C:max-instances/>` (the way `PrivateSkeletonOnly` serialises its precondition). It applies on **every** calendar mode, so it is not part of the Private write guard; catch it around the backend's object create/update (`GuardedCalendars`), and make sure the failed write leaves nothing behind: no object row, no `calendarchanges` row, no `caldav_changes` outbox row (E03-R10's transaction). The rejection log line carries no event content (the existing `Service::run` logs only `>= 500`).
3. A `calendar-query` that still overflows stays a `500` (the epic says so); don't widen it.
4. Every calendar collection answers `CALDAV:max-instances` = `50000` on `PROPFIND`, for every mode.
5. API: declare a new problem kind for the event write in `spec/openapi.yaml` **first** (status `422`; the occurrences endpoint already reports an object over the same bound as `too-many-instances`, so prefer that slug unless the problem table forbids reusing a word), then add it to `src/problem.mjs`'s table and map a CalDAV `403` carrying `max-instances` to it in `classifyCalDavError`, for create and update of an event (`src/events.mjs`). No request value or object byte reaches the problem document or a log line.
6. Keep `server/caldav/README.md` and `server/api/README.md` true for what you change; claim nothing in them you did not run.
