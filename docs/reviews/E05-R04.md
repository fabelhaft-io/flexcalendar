### Fix requests (one run)

1. **INV-05 in the generated client.** The generator copies the spec's descriptions into the Dart doc comments, and the scan (`/(?<![\w-])(?:EXDATE|RECURRENCE-ID)(?![\w-])/i`) flags the words. Reword every description in `spec/openapi.yaml` that names them ("the recurrence exceptions", "an occurrence id"), and add a unit test in `server/api/test` that applies the scan's expression to the spec file, so `make verify-server-api` fails before the clients are generated. Keep the TypeScript and Dart output out of it: I regenerate.
2. **Only valid objects.** After the merge, on create and on `PATCH`: `start` and `end` have the same value type (`date` with `date`, `utc` with `utc`), and `end` is later than `start`; otherwise the fixed `422`. A `PATCH` is checked against the stored object, not only its own members.
3. **Only valid, safe rules.** Accept exactly the parts RFC 5545 § 3.3.10 names (`FREQ` first and required, `UNTIL`, `COUNT`, `INTERVAL`, `BYSECOND`, `BYMINUTE`, `BYHOUR`, `BYDAY`, `BYMONTHDAY`, `BYYEARDAY`, `BYWEEKNO`, `BYMONTH`, `BYSETPOS`, `WKST`), each once, and any other part is a `422` rather than silently dropped; `COUNT` and `UNTIL` not together; `UNTIL` a `DATE` for an all-day start and a UTC `DATE-TIME` for a timed one. **And refuse what `ical.js` 2.2.1 expands wrongly** (my brief left this follow-up out; `docs/reviews/follow-ups/from-E15-R03.md` names E05-R04): any rule with `BYWEEKNO`, and `FREQ=YEARLY` on a 29 February start, until upstream moves (`spec/ical-fixtures/RULINGS.md`: `yearly-byweekno-20-monday-count-5`, `yearly-leap-day-all-day`). Say so in the README.
4. **An empty `PATCH` is a `422`.** Today `{}` writes a new revision: `SEQUENCE`, `DTSTAMP` and the `ETag` move although nothing changed, and every other client sees a change.
5. **A conditional `DELETE` of an object that is gone.** SabreDAV answers `412` to `If-Match` on a missing object (RFC 9110 § 13.1.1), so the live answer is `412` without `current` where the brief and your test title say `404`. When the re-read in `answerPreconditionFailed` finds nothing, answer the `404` an unknown `uid` gets; make the CalDAV double in `test/support/caldav-store.mjs` answer `412` to `If-Match` on a missing object, as SabreDAV does, so the test means something. The same race on `PATCH` (the object deleted between the read and the write) takes the same path.
6. **Framework errors are problems too.** A 201-character `uid` is answered by Fastify's own `400 {"error":"Bad Request","code":"FST_ERR_MAX_PARAM_LENGTH","message":"'/calendars/…'"}`: not problem+json, and the request path in the body (E05-R10's model: nothing in a body is derived from the request). Set Fastify's `frameworkErrors` in `buildApp` to answer these as the fixed `not-found` or `bad-request` problem, with a test through the real app (a 300-character `uid` and calendar id, and a malformed URL). Also close E11: the double records its calls, and the tests assert that a non-v4, non-canonical or overlong `uid`, and a malformed calendar id, never reach it.

Change nothing else.
