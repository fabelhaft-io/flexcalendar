**Security-relevant choices for the human approval** (each was run, not read):

1. **Access is derived from `public.calendar_members`, read from the database on every request**, with no cache: `getCalendarsForUser` joins the acting user's membership rows to the SabreDAV instance by `calendarinstances.uri = calendars.id`. A collection missing from the home is a 404 for every method and every href below it; a database error is a 500 and nothing is written, never an empty list.
2. **Roles map to exact privileges, spelled out in one table (`Access`)** and never through the `{DAV:}write` aggregate, because that aggregate contains `write-properties` and, for an `IACL` node, `write-acl`: viewer `read`; editor `read, write-content, bind, unbind`; owner adds `write-properties`; objects `read, write-content, write-properties` for editor and owner (so that a `PROPPATCH` of an object reaches the E03-R09 guard, which refuses every dead property of a Private object).
3. **Two layers.** Node ACLs (`MembershipCalendar`, `MembershipCalendarHome`, `MembershipCalendarRoot`) answer first and are what `current-user-privilege-set` advertises; the backend's write methods re-check the role (`createCalendarObject`, `updateCalendarObject`, `deleteCalendarObject`, `updateCalendar`, `deleteCalendar`, `createCalendar`) so that a path that skips the ACL plugin cannot get around them. The order is authorization, then the E03-R09 guard, then the E03-R10 transaction.
4. **Permissions never change through CalDAV:** `ACL` is refused for every principal, the owner included, and any `POST` to a calendar collection or object (the sharing extension's `share-resource`) is a 403 until E06-R03 reconciles shares.
5. **The role is read outside the transaction that writes**, so a downgrade in flight lets one already-authorized write finish; `calflex_caldav` has `SELECT` only on `calendar_members` and cannot take `FOR SHARE` on the row. Accepted and recorded for E08.
6. `MKCALENDAR` into the acting user's own home is unchanged: a collection without a `calendar_members` row is invisible to everyone, so creating one is harmless, and binding collections to rows is E05-R03.

Follow-ups for other requirements are in `follow-ups.md`: **E05-R03** (insert the `public.calendars` and owner `calendar_members` rows before or together with `MKCALENDAR`), **E06** (a pending member must already be a `calendar_members` row; a role change applies to the next request), **E03-R05 / Phase 4** (shares through Apple's extensions are refused until E06-R03), **E05-R10** (a `REPORT` with an empty or malformed body is a 500 instead of a 400, a shared-error-path issue found by a hand probe), **E08** (the role read outside the write transaction).

## Brief (condensed)

The home is the acting user's `calendar_members` rows, read on every request: a removed member's calendar is a 404 for every method and href. Roles map to exact privileges (viewer read; editor read, write objects; owner adds collection properties and deleting the collection), built from `calendar_members.role` with our own ACL nodes because `READWRITE` in SabreDAV's shared-calendar ACL would hand an editor `write-properties`. Permissions never change through CalDAV: `ACL` and `POST` refused for everyone. Enforced at two layers: node ACLs, and role checks in the backend's write methods, in front of the E03-R09 guard and the E03-R10 transaction.
