## Brief for run 1

### What is there (E03-R01 to R10, merged into this stack)

- `Service::create` builds the tree for **one acting user** (`$id` from the verified delegation header): `Principals` is read-only and returns only that user; `CalendarRoot` → `CalendarHome` per principal. A home of another user answers 404, and `MKCALENDAR` into it 409, exactly like an id that exists nowhere: **keep that**.
- Ownership today is SabreDAV's `calendarinstances.principaluri`. `GuardedCalendars` (extends `Sabre\CalDAV\Backend\PDO`) already wraps the object writes (E03-R09 guard, E03-R10 outbox transaction). `public.calendar_members (calendar_id, user_id, role owner|editor|viewer)` and `public.calendars (id uuid, mode, …)` are readable by `calflex_caldav`; a collection's URI is `calendarinstances.uri`, which holds `public.calendars.id`.
- What I read in sabre/dav 4.7.1 at `f36f002` (read, **not run**: write tests that fail if I am wrong):
  1. `CalendarHome::getChildren()` lists whatever `getCalendarsForUser($principalUri)` returns; the PDO backend implements `SharingSupport`, so each entry becomes a `SharedCalendar`. A node found through the home is the only way to reach a collection, so **a collection missing from the home is a 404 for every method and every href below it**.
  2. `SharedCalendar::getACL()` keys every privilege on `calendarInfo['principaluri']` and on `calendarInfo['share-access']` (`SharingPlugin::ACCESS_SHAREDOWNER=1`, `READ=2`, `READWRITE=3`). `CalendarObject::getACL()` keys on `principaluri` and `read-only`. The `PDO::getCalendarsForUser` query selects instances `WHERE principaluri = ?`.
  3. **Trap:** `{DAV:}write` is an aggregate that includes `write-properties`, and `ACCESS_READWRITE` yields it, so an "editor" built from `READWRITE` could `PROPPATCH` the collection. The requirement wants properties and deleting the collection for the **owner only**.
  4. `PDO::deleteCalendar` removes the whole calendar for the owner's instance and only the instance for a sharee.
  5. The `Sharing` plugin is not loaded, so `share-resource` bodies are not interpreted; the `ACL` method is DAVACL's. Neither is rejected today.

### The rules

- **The home is the membership.** For the acting user, `getCalendarsForUser` returns one entry per `calendar_members` row of that user (join `public.calendars.id::text = sabredav.calendarinstances.uri`), at `/calendars/<users.id>/<calendars.id>/`, read from the database **on every request, no cache**. A removed member's next request no longer lists it, and a `GET`, `PUT`, `PROPFIND`, `REPORT`, `DELETE`, or a `COPY`/`MOVE` destination or source under its href is **404, never 403**. A database error fails closed (a 500, nothing written).
- **Roles → privileges** (`calendar_members.role`): `viewer`: read (`GET`, `PROPFIND`, `REPORT`, `calendar-query`, `sync-collection`); `editor`: read, plus `PUT` (create and update) and `DELETE` of objects; `owner`: editor, plus `PROPPATCH` of collection properties and `DELETE` of the collection. A denied write is **403** (the node exists for them). `COPY`/`MOVE` need write on the destination collection, and `MOVE` also unbind on the source. The privileges must also be what the node advertises (`current-user-privilege-set`): stock apps (Phase 4) draw a viewer's calendar as read-only from it.
- **Permissions never change through CalDAV.** `ACL` → **403** for everyone, the owner included. A `POST` carrying a `share-resource` body (and any `POST` to a calendar collection) → **403**. `PROPPATCH` of `acl`-like or `invite`/`share` properties is rejected like any other property for a non-owner, and the owner's property writes still pass the E03-R09 allow-list.
- Do it at both layers if you can: node ACLs (what is advertised, and the 403 from the ACL plugin) **and** a check in the backend's write methods (`createCalendarObject`, `updateCalendarObject`, `deleteCalendarObject`, `updateCalendar`, `deleteCalendar`, `createCalendar`), so that no path that reaches the backend without the ACL plugin (a `COPY`, `MOVE`, an extended `MKCOL`) gets around it. The acting user is known when the backend is built.
- `MKCALENDAR` into the acting user's own home keeps working as in E03-R01 (it is not in this requirement; binding collections to `public.calendars` rows is E05-R03). A collection with no membership row is invisible to everyone. The E03-R09 guard and the E03-R10 outbox stay exactly as they are, and so does the order: authorization, then the guard, then the transaction.
- No new auth path, no header, no environment variable, no cache.
