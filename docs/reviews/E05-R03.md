## Brief for run 1

### What is already true

- Routes: `registerAuthRoutes` in `server/api/src/auth.mjs` registers `GET /me`; `resolveUser` there is not exported. `buildApp` in `app.mjs` runs the rate-limit hook, then the bearer hook, then the routes; the not-found and error handlers answer problems.
- Errors: `server/api/src/problem.mjs` owns the table (`PROBLEM_TYPES`: `invalid-input` 422, `precondition-failed` 412, `forbidden` 403, `not-found` 404, `conflict` 409, …; no 428), `sendProblem(reply, slug, { instance: request.id })` and `sendCalDavProblem(reply, error, { instance: request.id })`. A body never holds a request value or an exception message.
- The adapter (`server/api/src/caldav/adapter.mjs`) is the only module that reaches CalDAV: `adapter.forUser(userId, { requestId: request.id })` has `makeCalendar(calendarId)` (the fixed display name `Private calendar`) and `deleteCalendar(calendarId)`. Hrefs are `/calendars/<ownerId>/<calendarId>/`.
- Tables (E04): `calendars(id uuid, owner_id, mode calendar_mode, caldav_href text unique not null, meta_envelope bytea, meta_epoch int not null, created_at, updated_at)` with `CHECK ((mode = 'private') = (meta_envelope IS NOT NULL))` and `calendars_mode_private_only_check`; `calendar_members(calendar_id, user_id, role)` cascades; `event_envelopes` and the member keys cascade from them. There is **no version column**. Check the API role's grants (`1791496692783_core-tables-and-roles.mjs`): the grant on `calendars` decides whether a migration must add `UPDATE`.
- The CalDAV service reads `calendars` and `calendar_members` through its **own connection**: a collection with no committed rows is invisible to everyone (404 on every method), and `MKCALENDAR` of a UUID with no row still answers 201 and is treated as Private (E03-R08/R09). So the rows must be committed **before** `MKCALENDAR`.
- **`spec/crypto.md` does not exist yet** (E12-R01 is not merged). The envelope layout is in ADR 0001 § Private calendars — cryptography: byte 0 version `0x01`, bytes 1–4 the CCK epoch (uint32 BE), 24 bytes of nonce, ciphertext, 16 bytes of tag. The API links no crypto library (INV-07) and cannot check more than that.
- Spec: `docs/epics/E05-api-core.md` § E05-R03 and the paragraph above the requirements about `spec/openapi.yaml`; ADR 0001 § Decision; D-18; INV-01, INV-03, INV-07.

### What to build (design choices marked **mine** are the orchestrator's; say in the handoff if you deviate)

1. **Operations** in `spec/openapi.yaml` first, then routes: `GET /calendars` (the calendars the user is a member of: `id`, `mode`, `role`, `version`, `metaEnvelope`, `metaEpoch`, `createdAt`, `updatedAt`), `POST /calendars` (201 with `Location` and `ETag`), `PATCH /calendars/{id}` (rename and recolour are the same act: replace `metaEnvelope` and `metaEpoch`), `DELETE /calendars/{id}` (204). All with the `Problem` codes they can answer.
2. **Validation, all as 422 `invalid-input` with a fixed body** (never the value; the framework's schema-validation 400 stays for malformed JSON only, so do these checks in the handler or map them): `mode` missing; `mode` other than `private` (Phase 4 lifts `shared` and `published`; ADR 0003); `metaEnvelope` missing on create; an envelope whose header is invalid or whose decoded size is over 4096 bytes; a plaintext `name` or `color` on a Private calendar. **Mine:** `metaEnvelope` is standard base64 (OpenAPI `format: byte`) of the envelope bytes; the header check is "version byte `0x01`, epoch equal to `metaEpoch`, at least the 45 bytes of fixed fields". Put it in one small module with its own tests. Never log or echo the envelope.
3. **Identity.** Resolve `users.id` through the same function `GET /me` uses (E05-R01's review: one place for the first-sight rules); export or share `resolveUser`, do not write a second lookup. `calendars.id` is `crypto.randomUUID()` set by the API (INV-03, tested on the create path); `caldav_href` is `/calendars/<ownerId>/<calendarId>/`.
4. **Version.** **Mine:** a new migration (a new file; never edit an existing one) adds `version integer NOT NULL DEFAULT 1`, and every update sets `version = version + 1` and `updated_at = now()` in the same statement. `ETag: "<version>"` on every calendar response. `PATCH` needs `If-Match`: stale → 412 `precondition-failed`; absent → 428 (add `precondition-required` to the table and to the spec). Lost-update test: two PATCHes with the same `If-Match`, one wins.
5. **Create with compensation.** (a) One transaction inserts the `calendars` row and the owner's `calendar_members` row (`role = 'owner'`), and **commits**; (b) `makeCalendar`; (c) if (b) fails for any reason, delete the `calendars` row (the member row cascades) and answer through `sendCalDavProblem`; if the compensation itself fails, log the error name only and still answer 5xx. **Delete** is the other way round: `deleteCalendar` first (the owner can only reach the collection while the rows exist), a CalDAV 404 counts as already gone, then delete the rows; if the second step fails, answer 5xx and make the retry succeed. Test both failure orders with a fake adapter and a failing store, and that no row or collection is left over.
6. **Who may do what.** Only the owner renames, recolours or deletes. A non-member gets 404, identical to an id that exists nowhere (E03-R01); a member who is not the owner gets 403 `forbidden`. Phase 1 has no other members, but write the checks and the tests.
7. **405 with `Allow`** (E05-R10's review): Fastify answers 404 for a known path with another method, so `method-not-allowed` is declared and never sent. These routes are the first with several methods per path: make the 405 real, with an `Allow` header, for every registered path (`/me` and `/healthz` included), and add the case to the tests. Declaring `X-Request-Id` per operation in the spec is **not** required; leave it.
8. **A hostile exception** (E05-R10's mutation P5 survives because nothing sends one): add a route-level test where the store throws `new Error(<canary>)` → a 500 problem, and the canary is in neither the body nor the captured log.
9. **A CalDAV 401 is not the user's 401.** `classifyCalDavError` (`problem.mjs`) maps a CalDAV `401` to the `unauthorized` problem. In a user request the bearer token has already been verified, so a CalDAV 401 means our delegation failed (a bad key, or the service's database is down: it "answers 401 like a denial", E03-R01), and a client that receives a 401 for a valid token will sign the user out. **Mine:** map it to `bad-gateway` (502), change `problem.test.mjs` on purpose, and log nothing new. Say so in the handoff.
10. **Tests.** Database-free (fake store and adapter) for every Accept line: each 422 in the spec (POST without `mode`; Private POST without `metaEnvelope`; invalid header; over 4 KiB; plaintext `name`), UUIDv4 ids and hrefs, `If-Match`, the roles, 405, the canary. Database-backed in the style of `auth-db.test.mjs` for the transaction, the cascade and the version. In the stack (`server/api/test/integration/`, run by `make test-api-caldav`): create → the collection exists with the display name `Private calendar` and a second user cannot see it; PATCH → the collection is unchanged; delete → the collection answers 404; a marker inside `metaEnvelope` reaches neither log (extend the existing log scan the way E05-R10 did). Extend `contract.test.mjs` only as far as the new operations need.
