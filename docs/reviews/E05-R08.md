## Brief for run 1

### What is already true

- The pattern is `src/calendars.mjs` and `src/events.mjs`: routes declared in `spec/openapi.yaml` first, `resolveUser`, `calendars.findMembership(id, userId)` (a non-member is the 404 an unknown id gets), ids checked against the canonical lowercase UUID shape **before** the store is asked, `sendProblem` / `sendCalDavProblem`, `adapter.forUser(userId, { requestId: request.id })`, and Fastify's own refusals already answered as problems (`frameworkErrors`). A CalDAV `401` is a `502`, never the caller's 401.
- The adapter has `syncChanges(calendarId, token)` (`server/api/src/caldav/adapter.mjs`). It runs `sync-collection` with `d:getetag` and `c:calendar-data` and returns `{syncToken, changed: [{href, status, deleted, etag, data}]}`. `syncToken` is SabreDAV's `http://sabre.io/ns/sync/<n>`, where `<n>` is the number `public.caldav_changes.sync_token` also holds (E03-R10: `calendarchanges.synctoken + 1`); a deletion has `deleted: true`, no `etag` and no `data`; `data` is LF-normalised. Without a token it reports the whole collection (an initial sync). `test/integration/caldav-adapter.test.mjs` shows it against the real service: the initial report, one create, one delete as a tombstone.
- **SabreDAV does not tie a token to a collection**: its token is a plain per-collection number, so a token from another calendar is accepted and answers as if it were this one's. A token SabreDAV itself refuses (unknown, ahead of the collection, malformed) comes back as a `CalDavError`. E05-R02's follow-up says a route maps that to 410.
- Objects written by this API are named `<uid>.ics` (E05-R04). `public.caldav_changes(calendar_id, sync_token, uid, change_type)` is the E03-R10 outbox, readable by the API role; Phase 4 stock apps will write objects whose name is not their `UID`.
- Spec: `docs/epics/E05-api-core.md` § E05-R08; E07 (pings), the mobile app (Phase 3) and the web client (Phase 5) all use this endpoint.

### What to build (choices marked **mine** are the orchestrator's; say in the handoff if you deviate)

1. **`GET /calendars/{calendarId}/changes?since=<token>`**, in the spec first. Any member (`owner`, `editor`, `viewer`) reads; a non-member, an id outside the canonical shape and an unknown calendar are the same 404. Response, **mine:** `{token, changes: [{uid, etag, deleted}]}`. No `ical`, no `parsed`, no content: the client fetches what it needs with `GET …/events/{uid}` (E05-R05 serves windows). `etag` is CalDAV's, absent on a deletion. With no `since` the endpoint answers the whole collection as `deleted: false` entries and a token (the initial load).
2. **The token is ours and bound to the calendar, mine:** an opaque string the client never builds, made of the calendar id and SabreDAV's sync number (for example base64url of `<calendarId>:<n>`). A `since` that is not in that form, names **another calendar**, or carries a number SabreDAV refuses is **410** with the fixed problem (add `gone` to the operation's responses; it is already in the table), which tells the client to reload fully. Never pass a client-built string to CalDAV, never echo it, never log it.
3. **`uid`, mine:** for a present object, the `UID` inside `calendar-data` (parse it with the module `src/ical-rmw.mjs`, `parse` and `describe`), falling back to the name without `.ics`; for a deletion, the name without `.ics` when it is a UUIDv4. Where a deletion's name is not a UUIDv4 (not reachable before Phase 4) look the uid up in `caldav_changes` for that calendar and window rather than guessing; if it cannot be found, leave that entry out and say so in the README. Do not widen the API role's grants.
4. **Errors:** every refusal through the model; a CalDAV failure other than a refused token is `sendCalDavProblem`; the `410` body is the fixed problem, nothing of the request in it.
5. **Tests:** unit with the in-memory store and a CalDAV double (extend `test/support/caldav-store.mjs` so it implements sync-collection the way SabreDAV does: a numeric token per collection, **no** collection binding, a refusal for a number ahead of the collection): the token round trip; every kind of rejected token → 410 (malformed, another calendar's, ahead of the collection, SabreDAV's own refusal); roles; the same 404s as the other routes; no content, `ical` or token in a log (canary); a deletion has no `etag`. In the stack (`server/api/test/integration/`, run by `make test-api-caldav`): a create, an update and a delete between two tokens, **and each kind of rejected token → 410**, as the Accept line says; a token taken from another calendar of the same user must be 410 even though SabreDAV would accept its number.
