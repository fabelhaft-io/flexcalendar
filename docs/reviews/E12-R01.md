### Finding

- §6.6 step 3 (line 854): `crypto_box_seal_open(record[18:98], recipient_x25519_sk, record[18:50])`: the secret key where the public key goes, and the ephemeral key where the secret key goes;
- §6.7 (line 931): `crypto_box_seal_open(bundle[50:203], ephemeral_sk, bundle[50:82])`, the same mistake.

`generate.py:847` and `:954` do the same, and no vector reaches either function: the opening paths of the reference implementation have never run. A reader implementing §6.6 or §6.7 as written opens nothing.

### Fix requests

1. §6.6 step 3 and §6.7: `crypto_box_seal_open(sealed, recipient_pk, recipient_sk)`, where `recipient_pk = crypto_scalarmult_base(recipient_sk)` (say so: the caller holds the secret key and derives the public one) and `sealed` is the 80- or 153-byte `epk ‖ tag ‖ c` span. Check every other libsodium call the spec writes out for its argument order against libsodium's documented signature.
2. `generate.py`: fix both openers the same way, and make the generator **run every opener against its own vectors** as a self-check (each `open_*` vector through the matching function, positives to their expected output, negatives to their expected code), so no function in the reference implementation is dead code. ### Findings (the spec text; the vectors and the generator are right)

1. **§6.6 (line 804) and §6.7 (line 888) put the sealed box's tag after the ciphertext.** libsodium's `crypto_box_easy`, and therefore `crypto_box_seal`, writes the 16-byte Poly1305 tag **first**: my check, `crypto_box_easy` of 32 bytes vs `crypto_box_detached`'s `mac`, gives `easy[0:16] == mac: true`, `easy[32:48] == mac: false`. Someone implementing the record without libsodium would lay it out wrongly.
2. **§6.6 (line 817) and `gen/README.md` (line 75) name the seal nonce `BLAKE2b-256(epk ‖ recipient_pk)`.** libsodium derives it with BLAKE2b at a **24-byte output length** (`crypto_generichash` with `outlen = crypto_box_NONCEBYTES`), a different function from BLAKE2b-256, not a truncation of it. `generate.py:666` does it right (`hashlib.blake2b(…, digest_size=24)`), and that is why the vectors open.
3. **§2.1 (line 190):** "12 bytes of `"calflex-v1"`"; the label is 10 bytes.
4. **§2.4 (lines 232–235):** "Two more labels" and then three (`calflex-id-v1`, `calflex-safety-v1`, `calflex-link-code-v1`); and "none of them is ever used as an AEAD AAD except the three in the table's first two rows and `calflex-keywrap-v1`" counts three labels in two rows. Say exactly which labels are AEAD AADs (`calflex-v1`, `calflex-meta-v1`, `calflex-keywrap-v1`) and which are signed messages.

### Fix requests

1. Fix the four places above: the tag-first layout in §6.6 and §6.7's offset tables (tag 16 bytes, then the 32- or 105-byte ciphertext), the 24-byte BLAKE2b nonce in §6.6 and `gen/README.md`, the label length in §2.1, and §2.4's label sentences.
2. Add a vector, or a field in the existing `cck-record-seal-basic`, that carries the derived 24-byte seal nonce for its fixed ephemeral key, so a reader without libsodium can check finding 2.
3. Re-run `generate.sh --check` and paste its output in the handoff.

## Brief for run 1

The requirement is in `docs/epics/E12-crypto-core.md` § E12-R01; the spec it formalises is ADR 0001 § Private calendars — cryptography (with its amendments) and the Pinned decisions D-06, D-08, D-14, D-15, D-16, D-17 and D-18 in `docs/06-implementation-backlog.md`. Executor `agent+review`: the owner approves the PR before merge. Writable paths: `spec/crypto.md` and `spec/crypto-vectors/`. No library code (`packages/**` is E12-R03/R04), nothing under `server/**` (INV-07).

### Deliverables

1. **`spec/crypto.md`**, every byte of every item the epic lists, written so a reviewer can implement from it alone: field order, lengths, endianness, encodings (hex case, base64 alphabet and padding), version bytes, domain-separation labels, and what a reader must refuse. Every format carries a version byte or label, so a later change is a new version rather than a silent break.
2. **`spec/crypto-vectors/gen/`**: the **independent reference implementation**, in Python 3 with PyNaCl (PyPI 1.6.2 on 2026-10-12) and, for JCS, either `rfc8785` (0.1.4) or a short hand-written serialiser that the spec's examples check. Pin every dependency exactly with hashes (`requirements.txt` with `--hash`, or `uv.lock`), and give one command that regenerates every vector from fixed, invented inputs. It must not import, shell out to or copy from the Dart or TS libraries (they don't exist yet; keep it that way).
3. **`spec/crypto-vectors/*.json`**: positive vectors for every field and format, and **negative** vectors a library must refuse (wrong version, truncated envelope, flipped tag, flipped AAD field, wrong `calendar_id`, wrong `recurrence_id`, an event envelope opened as a metadata envelope and the reverse, a CCK record with a bad signature, a recovery code with a bad checksum). A check in `gen/` regenerates the vectors into a scratch directory and fails if they differ from the committed ones; run it.

### Pinned decisions the spec must respect (never change one; a conflict is an open question)

- **D-17: the recovery-code KEK is HKDF.** `docs/verification/crypto-libs-2026-10-12.md` (E12-R02) found that `libsodium-wrappers` exports no HKDF function and recommends `crypto_kdf`. That recommendation does **not** override D-17. HKDF-SHA-256 is available on the web through WebCrypto (`crypto.subtle`, HKDF is native there) and in Dart through `sodium`'s `KdfHkdf`, whose `info` is a `String` encoded as UTF-8: so make every HKDF `info` an ASCII label, and say so. Where the spec derives something D-17 does not cover, it may pick `crypto_kdf` (BLAKE2b), with the reason written down. No Argon2id, no key from any password (INV-12).
- **D-14:** the AAD includes `calendar_id` and `recurrence_id`, in a fixed order after `"calflex-v1"`, each length-prefixed u32 BE.
- **D-15:** CCK records and key bundles are signed with the per-user Ed25519 identity key; define the identity-key fingerprint, the safety-number format and the QR payload.
- **D-18:** the calendar-metadata envelope has its own domain label, the `calendar_id` and the epoch in its AAD, so it can never open as an event envelope (a negative vector shows it).
- **D-06 / E04-R04:** `X-CALFLEX-ENVELOPE-SHA256` is 64 lowercase hex digits of the SHA-256 of the complete envelope bytes, and the canonical `recurrence_id` is the encoding `docs/epics/E04-data-model.md` § E04-R04 pins (an instant; read the section and `server/api/src/recurrence-key.mjs`, which implements it). Use exactly those, and give vectors that show two spellings of one instant producing one key.
- **D-08:** a `VALARM` stays cleartext with `DESCRIPTION:Reminder`; it is not in the envelope.

### Follow-ups that belong to this requirement (from `docs/reviews/follow-ups/`)

- **Signer of a CCK record** (from-E04-R05): the sealed and signed CCK record carries its signer's user id, because `calendar_keys` has `calendar_id`, `epoch`, `user_id` (the recipient) and the opaque `record` only. State the size limits the API should enforce for wrapped private keys and records (the database has none).
- **Envelope header and epoch** (from-E05-R03): the API already checks the header as ADR 0001 lays it out (`server/api/src/calendar-envelope.mjs`: `ENVELOPE_VERSION`, `ENVELOPE_FIXED_BYTES = 45`, `MAX_ENVELOPE_BYTES = 4096`). Either match those constants or name the differences for a follow-up on the API. The epoch is a u32 on the wire but `integer` in Postgres: **cap the epoch at 2,147,483,647** in the spec (the cheaper side), with a negative vector at 2^31.
- **DST answers for the AAD's timing fields** (from-E04-R04, from-E15-R02): the canonical timing fields are computed from parsed values. Pin RFC 5545 § 3.3.5's answers, the ones in `spec/ical-fixtures/dst/cases.json`: a nonexistent local time uses the offset before the gap, a repeated one the first occurrence; and the `daily-skipped` ruling of 2026-10-12 (`docs/02` § Recurrence: the instance is kept and placed at the offset before the gap). Vectors for `Europe/Berlin` `20260329T023000` and `20261025T023000` show both. `ical.js` gets both wrong with a `VTIMEZONE` (it gives `…T003000Z` for the gap and the second occurrence for the overlap), which is why the binding is to parsed values computed the RFC's way, not to any library's reading.
- **Zone data** (from-E05-R09): the components carry different tz versions; say which canonical form the AAD binds (the `TZID` and the local wall clock, or the UTC instant), and why that choice survives a tz update without breaking an existing envelope.
- **RDATE/EXDATE**: the epic requires the spec to state, with reasons, whether they are bound. Remember INV-05: clients never emit `EXDATE` or `RECURRENCE-ID`; the API writes them, so an `EXDATE` the API adds after sealing must not invalidate the master's envelope if the spec binds it.

### Rules

- Every key, nonce, seed, code and event in the vectors is invented and labelled as a test value. No secret.
- Keep the vectors deterministic: fixed nonces and keys as inputs; a sealed box (random by construction) gets a vector for opening a fixed ciphertext rather than for sealing.
- Write `spec/crypto.md` and the vectors completely even if some tool is missing in the sandbox; prove a missing tool with its command and output. Run the generator and its check for real, and paste the commands into `openQuestions` for the reviewer.
