### What to build (choices marked **mine** are the orchestrator's; say in the handoff if you deviate)

1. **The route, mine.** `GET /calendars/{calendarId}/occurrences?from&to&tz`, defined in `spec/openapi.yaml` first (operation `listOccurrences`; every status the other calendar routes document; `405` through `src/allow.mjs` needs nothing). `from` and `to` are required instants in the API's own form, `YYYYMMDDTHHMMSSZ`; `to` later than `from`, and a window of at most 1830 days; `tz` is optional, an exact-spelling IANA name through `isIanaZone`, default `UTC`. Anything else is the fixed `422` problem. The response is `{occurrences: [...], unsupported: [...]}`. Caller who is not a member, unknown or non-canonical id → the 404 the events routes give.
2. **The source, mine.** `listObjects` with the window padded by one day each side (an all-day event and a zone offset up to ±14 h must not fall out of CalDAV's own filter), then the exact filter in the module. No pagination: more than 10,000 occurrences in one answer is the `422` `window-too-large`; per object, the expansion stops at 50,000 iterations from `DTSTART` and the object is reported in `unsupported` (reason `too-many-instances`), never as a 500.
3. **`src/occurrences.mjs`, a pure module, mine:** `expandOccurrences(objects, {from, to, tz})`, `objects` being `{href, etag, ical}`. No I/O, no clock. Each object holds one master and its overrides.
4. **How to expand, mine.** Let `ical.js` do only the recurrence arithmetic, on **wall-clock** values, and take every instant from `src/zones.mjs`: expand a floating copy of the master (its `TZID` parameters removed from `DTSTART`, `RDATE`, `EXDATE`; `RECURRENCE-ID` matched as wall clock), then map each wall clock to its instant with `instantOf`. A `UTC` start needs no zone; an all-day event stays a date. `UNTIL` beside a zone start is UTC (RFC 5545 § 3.3.10): convert it with `localOf` before the floating expansion and test it on the instant either side. An unknown zone or a Windows name in the object (a stock app's) → the object is in `unsupported` with reason `unknown-zone`, expanded as nothing, never guessed. The two `ical.js`-wrong rule families above → `unsupported`, reason `rrule-not-expanded`. A cleaner design that keeps both constraints (no `ical.js` instant, no global registration) is welcome; say so.
5. **A series that crosses a gap, mine and provisional.** An instance whose wall clock does not exist is kept, counted, and read with the offset before the gap (the `alternative` of the table; it is what `sabre/vobject` does, so a stock app and our app agree). Put that in **one named constant or function** with a comment pointing at the pending ruling, so that the owner's decision is a one-line change. The DST runner reports it.
6. **An occurrence, mine.** `{uid, recurrenceId, override, start, end, allDay, envelopeSha256}`. `start`/`end` are the instant in the requested `tz`: `{utc, local, tzid}` (`tzid` is the requested zone), or `{date}` for an all-day event (no zone, no instant). `recurrenceId` is the instance's original start in the form the object stores it (`{utc}`, `{date}` or `{local, tzid}`, the same shape as an event time), so R06/R07 can send it back; `null` for a non-recurring event. `override` is true for an instance an override `VEVENT` defines. `envelopeSha256` is the `X-CALFLEX-ENVELOPE-SHA256` of the `VEVENT` that defines the instance (the master for a derived one, the override's own otherwise), or null. The end of a derived timed instance is its start plus the master's exact duration (end instant − start instant); an all-day one is whole days. An override uses its own times.
7. **Which occurrences are in the window, mine.** An instance is in if its interval overlaps `[from, to)`: `start < to` and `end > from`; a zero-length instance is in when `from <= start < to`. **Inclusive start, exclusive end, everywhere.** An all-day instance covers `[date 00:00 in tz, next date 00:00 in tz)` as instants (23, 24 or 25 hours on a transition day). An override replaces the master instance it names whether or not its own times are in the window, and is itself reported by its own times; `EXDATE` removes an instance; `RDATE` adds one; output sorted by start instant, then `uid`, then `recurrenceId`.
8. **Tests.** Route tests through the real app with a fake adapter (the events tests show how). **The DST runner:** read `spec/ical-fixtures/dst/cases.json` from the file, never a copy, and for each case build the object, run `expandOccurrences`, compare instants to `expected`: `skipped`, `repeated`, `control`, `daily-existing` equal; `view-zone` compares `start.local` with `tz = input.viewZone` to `expectedLocal`; `all-day`: the occurrence is in a window of exactly `[expected[0], expected[1])` and out of the windows `[expected[0] - 1 day, expected[0])` and `[expected[1], expected[1] + 1 day)`; `daily-skipped`: accept `expected` or `alternative`, report which matched with `t.diagnostic`, and mark the kind `todo` (the ruling is pending: it must neither fail nor be called green). **The corpus runner:** all 34 `rrule/` fixtures through `expandOccurrences`, normalised to the golden's form by a post-process that lives in the test (pad the window, keep an occurrence whose own start is in the corpus window, an override whose `recurrenceId` is in it), compared to the goldens with the E15-R03 helpers. If a fixture differs from its golden and `RULINGS.md` has no entry for exactly that, **do not edit the golden or the rulings and do not bend the module**: list the fixture and the first difference in `openQuestions` and stop on that point. **Window edges and unbounded rules (the gap `from-E15-R03.md` names, covered here by the module's own tests rather than by new corpus files):** an unbounded weekly rule, an unbounded `FREQ=MONTHLY;BYMONTHDAY=-1`, an unbounded all-day rule, an instant exactly on `from` (in), exactly on `to` (out), one second either side, an all-day event the day before `from` (out) and the day containing `from` (in) for a `tz` ahead of UTC and one behind it, a `DTSTART` years before the window, a multi-day event that starts before `from`. Overrides: moved into the window (in), moved out (out, and the master instance still gone), an `EXDATE`, an `RDATE`, an override with an unknown `RECURRENCE-ID`. The hostile-exception test (E05-R03's pattern) for the route.
