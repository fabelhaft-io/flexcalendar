The root case works by setting `VCalendar::$defaultName`, because MimeDir parses only `VCALENDAR` and `VCARD` on the wire; it restores the value in `finally`. It is a hack, and it is what makes the engine's own root check testable.

**Security choices for the owner's approval** (each was exercised, not read):

1. **Where**: the storage backends (`Backend\PDO::createCalendar`, `updateCalendar`, `createCalendarObject`, `updateCalendarObject`, and the PropertyStorage `propPatch`), not HTTP events. `COPY`, cross-collection `MOVE`, the extended `MKCOL`, jCal and `REPAIR` are covered by that seam (a mutation that skips the guard for the `COPY`/`MOVE` payload alone fails its own case).
2. **Mode**: read per call from `public.calendars`, no cache. No row, a non-UUID segment, an unexpected value: Private rules. A database error propagates (a 500, nothing written). Only `shared` and `published` bypass.
3. **Answer**: 403 with `DAV:error` holding `cf:private-skeleton-only` and `cf:name`; the name is the parsed property, parameter or component name, and only inside `[A-Z][A-Z0-9-]{0,63}` (otherwise `UNLISTED`); a fixed exception message; no `error_log` in the guard. No probe response carried a `DAV:message`.
4. **Strictness beyond the table's words**: one hash on **every** `VEVENT`; grouped properties and trailing bytes after `END:VCALENDAR` rejected; `displayname` may be absent but never removed or changed; every dead property on an object in a Private calendar rejected; `supported-calendar-component-set` and `calendar-timezone` rejected on creation.
5. **Log scan**: `make test-caldav` also greps for `CALFLEX_GUARD_MARKER`. A guard that logs the rejected body, an unlisted value or a collection value fails it while PHPUnit stays green; with the regexp reverted the same mutation passes, so that one edit is what catches it.
6. **What the guard cannot do**: the free-text values of allowed properties pass (`UID`, `PRODID`, a `TZID` parameter, `TZURL`, `X-LIC-LOCATION`, `TZNAME`): `UID:Chemo with Dr Smith` was accepted. Said in the README. The owner decides in `follow-ups.md` whether Private `UID`s are pinned to UUIDv4.

Follow-ups for other requirements are in `follow-ups.md`: the `UID` question above; **E05-R09** (an embedded `VTIMEZONE` stays inside the allow-list: tzurl.org's `X-PROLEPTIC-TZNAME` is rejected); **E03-R08 / E05-R03** (`MKCALENDAR` of a non-UUID name, or of a UUID with no `public.calendars` row, answers 201 and is treated as Private); **E05-R04 / E05-R10** (the API maps the `cf:name` element to its problem+json, never a value); **E13-R06** (real-SQL `shared` and `published` lookup cases once the check is lifted); **E08** (each rejection logs `caldav dav_failure`); a pre-existing `500` for the `MKCOL` of a subscription (nothing stored; SabreDAV's `Subscriptions` plugin is not loaded).
