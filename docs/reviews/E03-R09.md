## Brief for run 1

### What is there (E03-R01, merged)

- `Service::create()` builds the SabreDAV server; `Service::run()` calls `invokeMethod` and, on any throwable, `Service::errorResponse()`. **Errors leave the service as SabreDAV's serialized `DAV:error` document through `errorResponse`**: it calls `Exception::serialize()` and `getHTTPHeaders()`, never the message, class or trace. So `cf:private-skeleton-only` is an exception element: a `Sabre\DAV\Exception\Forbidden` subclass whose `serialize()` appends `<cf:private-skeleton-only xmlns:cf="https://flexcalendar.de/ns/caldav"/>` plus the name (below). Do not make `errorResponse` print more.
- The tree is `/calendars/<users.id>/<calendars.id>/`. The collection URI is `sabredav.calendarinstances.uri`, which holds `public.calendars.id` (a UUID). `calflex_caldav` has `SELECT` on `public.calendars`; `calendars.mode` is an enum and only `private` can exist before Phase 4.
- `tests/EventFixture.php` builds an event with `SUMMARY` and no envelope hash, and `ServiceTest` PUTs it into a calendar whose `public.calendars` row is `private`. With the guard those PUTs are rejected. Make the fixture a **valid skeleton** (the hash, no `SUMMARY`, the `RRULE` and the `Europe-Berlin.ics` `VTIMEZONE` stay) and keep content only in the rejected cases. `ServiceTest` also sends `MKCALENDAR` with no body: no display name is accepted (nothing to leak).
- `make test-caldav` runs the one-off `caldav-test` service (`tests/Integration` only). `composer test` runs `tests/Unit` on the host. `README.md` says the guard is "R08–R10": update it, and keep every claim true.

### Where the guard goes

What I read in sabre/dav 4.7.1 at `f36f002` (read, **not run**: write tests that fail if I am wrong, and say so in `openQuestions`):

1. `beforeCreateFile` and `beforeWriteContent` fire from `Server::createFile/updateFile`, which only `CorePlugin::httpPut` calls. `COPY` and cross-collection `MOVE` go `Tree::copy` → `Calendar::createFile` → `Backend::createCalendarObject` and fire neither.
2. The CalDAV plugin may rewrite a PUT body before it is stored (jCal to iCalendar; `REPAIR` unless `Prefer: handling=strict`). A guard that parses the request sees other bytes than the ones stored. The backend gets the stored string.
3. `MKCALENDAR` and the extended `MKCOL` (RFC 5689) both reach `CalendarHome::createExtendedCollection` → `Backend::createCalendar($principalUri, $uri, $properties)`, before any `propPatch` event. `PROPPATCH` on a calendar reaches `Backend::updateCalendar($id, PropPatch)`. `PROPPATCH` on an **object** reaches only the PropertyStorage plugin, whose backend `propPatch($path, PropPatch)` stores any dead property in `sabredav.propertystorage`: in Phase 1 that stores plaintext beside a Private event.

So guard the **backends**: a subclass of `CalDAV\Backend\PDO` overriding `createCalendar`, `updateCalendar`, `createCalendarObject`, `updateCalendarObject` (`$calendarId` is `[calendarId, instanceId]`; the UUID is `calendarinstances.uri` of that instance), and a subclass of `PropertyStorage\Backend\PDO` for `propPatch` under `calendars/<user>/<uuid>/…`. E03-R10 will hook the same object methods. Integration cases for `COPY`, `MOVE`, extended `MKCOL`, `PROPPATCH` on a calendar and on an object must each end rejected, or show that content cannot get through.

### The rules

- **Mode**: `SELECT mode FROM public.calendars WHERE id = ?` per call, on the service's connection, no cache that outlives the request. Match the segment against a UUID pattern first (`WHERE id = 'foo'` is a PDO error, so a 500). **No row, or a non-UUID segment: apply the Private rules** (the strictest; the API may create the row after the collection, and nothing else exists before Phase 4). A database error fails closed. Shared and Published collections are not guarded; cover that path in a unit test with an injected lookup, because the integration suite cannot create one before E13-R06.
- **Engine**: a pure function over the iCalendar text and over a property array, with no PDO and no Sabre in it, parsed with `sabre/vobject` (already installed; no new package), unit-tested in `tests/Unit`. It is an allow-list exactly as in E03-R09's table. Traps:
  - the hash is required on **every** `VEVENT` (master and each override), exactly one, `/\A[0-9a-f]{64}\z/` (a bare `$` accepts a trailing newline);
  - components: `VCALENDAR` → `VEVENT`, `VTIMEZONE`; `VEVENT` → `VALARM`; `VALARM` → nothing; `VTIMEZONE` → `STANDARD`, `DAYLIGHT`; those → nothing. Unknown and `X-` components are rejected;
  - parameters: `TZID`, `VALUE`; `RANGE` only on `RECURRENCE-ID`; `RELATED` only on `TRIGGER`. A parameter that is fine elsewhere is rejected on the wrong property;
  - unlisted properties are rejected by default: test `TRANSP`, `PRIORITY`, `X-ANYTHING`, `METHOD` on the `VCALENDAR`, `COMMENT` inside `STANDARD`, a lowercase `summary:`;
  - `CALSCALE` only `GREGORIAN`; `VALARM` `DESCRIPTION` exactly `Reminder`;
  - collection properties: only `{DAV:}displayname` equal to `Private calendar` (absent is fine). Everything else is rejected, `supported-calendar-component-set` and `calendar-timezone` included.
  - Add no rule the table lacks (floating times, `DTEND` against `DURATION`, value formats). List such ideas in `openQuestions`.
- **Rejection**: 403 with the precondition. It names the offending property, parameter or component, never a value. Names are client text too: echo one only if it matches `/\A[A-Z][A-Z0-9-]{0,63}\z/`, otherwise a fixed placeholder; take it from the parsed name, never from a raw line. The exception message is a fixed string. **No `error_log` in the guard**: `Service::run` already logs the one fixed line `caldav dav_failure`.
- A body that does not parse never reaches the backend: the CalDAV plugin answers 415 with the parser's message inside the exception, which `errorResponse` leaves out. Keep it so, and test it.
