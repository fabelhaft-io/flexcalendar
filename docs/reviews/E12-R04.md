# Review — E12-R04 · Key hierarchy

## Brief for run 1

The requirement is in `docs/epics/E12-crypto-core.md` § E12-R04. **Phase 2: the Dart library only**; the TS half is Phase 5. The spec is `spec/crypto.md` (accepted 2026-10-12): §6.1 key material, §6.2 the key bundle, §6.3 the wrapped private key and §6.3.1 the recovery-code KEK (HKDF-SHA-256, D-17), §6.4 the recovery code (BIP-0039), §6.5 the CCK, §6.6 the sealed and signed CCK record (D-15), §6.7 device linking, §6.8 identity fingerprints, safety numbers and the QR payload; and the vectors `keys-v1.json`, `cck-records-v1.json`, `device-link-v1.json`, `identity-v1.json`. Executor `agent+review`. Writable paths: `packages/crypto_dart/`.

**This branch is stacked on E12-R03** (`feat/E12-R03-envelope-seal-open`, PR #101, waiting for the owner): the package, its `sodium`/`timezone`/`crypto` dependencies, the error codes (`lib/src/errors.dart`) and the vector loader (`test/vectors.dart`) are already there. Reuse them; don't start a second structure.

### What to build

- User keypair generation: X25519 for sealing and Ed25519 for signing (D-15), from the CSPRNG; the key bundle of §6.2.
- The recovery code: 128 bits of entropy, BIP-0039 English (12 words), parse back with §6.4's rules (lowercase, split on U+0020 or U+3000, exactly 12 known words, the checksum) → `E_RECOVERY` before any derivation; `KEK_rc` by HKDF-SHA-256 with §6.3.1's ASCII salt and info; wrap and unwrap of the key bundle under it (§6.3: XChaCha20-Poly1305, its own AAD, kinds, `E_UNSUPPORTED` for the reserved escrow kind), and the unwrap check that the keys match the expected public keys.
- Device linking (§6.7): the bundle sealed to a new device's ephemeral X25519 key, signed, the verification code and the `calflex://link/1` URI.
- The CCK: generation, sealing to a member and signing with the sender's identity key (§6.6), opening with the signature checked **first**.
- Identity fingerprints, safety numbers and the `calflex://verify/1` QR payload (§6.8).
- **No function takes a password** (D-17, INV-12): no `crypto_pwhash`, no Argon2id, nothing that derives from a login secret.

### Facts and constraints

- **The word list:** vendor BIP-0039's `english.txt` (bitcoin/bips) into the package with its provenance and licence recorded, and a test that its SHA-256 is `2f5eed53a4727b4bf8880d8f3f199efc90e58503646d9ff8eff3a2ed3b24dbda` (§6.4). `spec/crypto-vectors/gen/english.txt` is the same file.
- **Sealed boxes** (§6.6): `crypto_box_seal_open(c, pk, sk)` takes the **public key first**; the box is `epk ‖ tag ‖ c` (tag first); the seal nonce is BLAKE2b with a 24-byte output (`cck-records-v1.json`'s `seal_nonce_hex`). A sealing vector names its fixed ephemeral key: expose a **test-only** seam for it, never in the public API.
- **HKDF** in Dart: `sodium`'s `KdfHkdf` takes `info` as a `String`; every `info` in the spec is ASCII.
- **INV-05** scans `packages/crypto*`: never name the recurrence properties anywhere in the package, comments included (E12-R03's review 2).
- **Tests** read every positive and negative vector of the four files directly from `spec/crypto-vectors/`, assert each to its bytes or its exact error code, and fail if a file contributes none; any expectation built on a random seal must not depend on the random bytes (E12-R03's review 3).
- From `docs/reviews/follow-ups/from-E12-R03.md` (on PR #101's branch): `openEvent`/`openCalendarMetadata` return bytes; tolerate additive `expected` keys.

### What the sandbox can't run

The gate needs the `sodium` build hook (a C compiler) and the pinned Dart. Run `make verify-packages-crypto_dart` **and** `make verify-tooling` (INV-05) if you can; prove a missing tool with its command and output.
