## Goal

Two small libraries, `packages/crypto_dart` (Phase 2) and `packages/crypto-ts` (Phase 5), that produce byte-identical results from one written spec and one set of test vectors. The vectors are frozen in Phase 2, so the TS library has a fixed target. Nothing on the server links either of them (INV-07).

## Requirements

### E12-R01 · Written wire spec   `agent+review`
`spec/crypto.md` MUST define every byte:
- the envelope layout from ADR 0001 (version, epoch, nonce, ciphertext, tag);
- the **canonical AAD encoding**: `"calflex-v1"`, then length-prefixed (u32 BE) UTF-8 fields in a fixed order, including the fields D-14 adds;
- the payload: JSCalendar (RFC 8984) field names, serialised with JCS (RFC 8785);
- the formats of wrapped private keys, sealed CCK records (per D-15) and recovery-code encoding;
- the device-link message (E14-R08): ephemeral public key, short verification code, sealed key bundle;
- the **calendar-metadata envelope** (D-18): the calendar's name and colour, sealed under the CCK, with an AAD that carries its own domain label, the `calendar_id` and the epoch, so it can never be confused with an event envelope;
- the **skeleton bindings**:
  - `X-CALFLEX-ENVELOPE-SHA256` and the canonical `recurrence_id` use exactly the encodings pinned in E04-R04;
  - the AAD's canonical timing fields (`DTSTART`, `DTEND` or `DURATION`, `RRULE`) are computed from parsed values, so re-serialising the skeleton with `ical.js` (E05-R07 plans) can't change them;
  - the spec states, with reasons, whether `RDATE` and `EXDATE` are bound;
- the **identity-key fingerprint**, the safety-number format and the payload of the key-verification QR code (D-15), used by E06-R09, E13-R05 and E14-R05.
- Per D-17 there are no Argon2id parameters. They return only if a separate passphrase option is ever added.
- Accept: a reviewer can implement from the spec alone; every field has a test vector.
- Accept: the vectors in `spec/crypto-vectors/` are generated by an **independent reference implementation**, a small script outside the Dart and TS libraries, for example Python with PyNaCl, kept under `spec/crypto-vectors/gen/`. The libraries are then tested against something other than themselves.
- Deps: E12-R02, which settles which primitives (HKDF in particular) the libraries really offer.

### E12-R02 · Library capability check   `agent`
Before writing any implementation, a check MUST confirm that `sodium_libs` (Flutter) and `libsodium-wrappers` (web) provide XChaCha20-Poly1305-IETF, `crypto_box_seal`, Ed25519 and HKDF/`crypto_kdf` (ADR 0002 says to verify, not assume). It is executed on an Android emulator or device and on the Dart VM, and for the web library under Node. **iOS is not checked before Phase 5**: E10's iOS build repeats this check there.
- Accept: `docs/verification/crypto-libs-<date>.md` records the versions, the commands run with their output, and any gaps.
- Notes: the non-sumo `libsodium-wrappers` build lacks `crypto_pwhash` and some other primitives. Without Argon2id (D-17) it may be enough; check every primitive above before choosing it over the larger sumo build.

### E12-R03 · Envelope seal/open   `agent+review`
Both libraries (Dart in Phase 2, TS in Phase 5) MUST implement `seal(cck, epoch, skeleton, payload) → bytes` and `open(cck, bytes, skeleton) → payload` per R01, with a random 24-byte nonce for every seal. They MUST also seal and open the calendar-metadata envelope (D-18).
- Accept: all positive and negative vectors pass: a tampered AAD field, a wrong epoch, truncation, a wrong version, a flipped tag bit, and an event envelope opened as calendar metadata or the reverse. Open never returns partial plaintext.
- Deps: E12-R01.

### E12-R04 · Key hierarchy   `agent+review`
Implement:
- user keypair generation (X25519 for sealing, plus Ed25519 for signing per D-15);
- a recovery-code KEK via HKDF, and wrap and unwrap of the private keys under it;
- device-link sealing of the private keys to a new device's ephemeral X25519 key;
- CCK generation, and sealing a CCK to a member, signed with the sender's identity key.

Per D-17, no KEK is derived from the login password.
- Accept: the vectors pass in Dart (Phase 2) and TS (Phase 5); from Phase 5 a key wrapped in Dart unwraps in TS and the reverse; no library function accepts a password (INV-12).
- Deps: E12-R01.
- Notes: per D-16, the Dart library owns recovery-code, Shamir and escrow wrapping; the TS library implements the operational subset only.

### E12-R05 · Cross-language vectors in CI   `agent`
`spec/crypto-vectors/*.json` (generated once and then frozen) MUST be run in `make verify` by the Dart library from Phase 2, and by both libraries from Phase 5.
- Accept: changing a single byte in either library's output fails CI; adding a field to the spec without a vector fails a completeness check. The vectors run under `make verify-corpus` (E02-R04).
- Deps: E12-R03, E02-R04.

### E12-R06 · Key storage on device (Phases 3 and 5)   `agent+review`
Mobile (Phase 3) keeps the unwrapped private keys in `flutter_secure_storage`, which is Keystore-backed on Android. Web (Phase 5) keeps them in memory. It may also persist them in IndexedDB, wrapped by a non-extractable WebCrypto AES-GCM key, so that a page reload doesn't require device linking or the recovery code again (D-17: no password ever unlocks keys).
- Accept: sign-out wipes both; a test checks that keys never reach `localStorage` or logs.
- Deps: E10-R01, E10-R02 (mobile); E09-R01 (web).

### E12-R07 · Shamir 2-of-3 (Dart, Phase 7)   `agent+review`
A k-of-n Shamir split over GF(256) for the recovery secret, used by E14-R05. Use an audited package if one exists; otherwise a minimal implementation with published test vectors.
- Accept: any 2 of 3 shares reconstruct; a single share reveals nothing (statistical test over the vectors); shares carry an index and a checksum.
