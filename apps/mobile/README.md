# `apps/mobile/` — Flutter mobile app

**Owning epic:** [E10 — Flutter mobile app](../../docs/epics/E10-mobile-app.md).

- **What belongs here:** one Flutter (Dart 3) codebase for Android (minSdk 26)
  and iOS 16+, with Riverpod, `dio` plus the client generated from
  [`spec/openapi.yaml`](../../spec/openapi.yaml), Drift (SQLite) for the offline
  cache, `timezone` for every `TZID` calculation (never raw `DateTime` — INV-04),
  and flavors `dev|staging|prod` (ADR 0002,
  `docs/02-technology-choices.md` § Mobile clients). The app is a REST client:
  it never talks to CalDAV itself, and it sends recurring-event edits as intents
  (INV-05).
- **`android/`** holds the Flutter project's Android module. From Phase 6 it
  also holds the native Kotlin `CalendarContract` sync adapter, with **no Dart
  in its sync path** — see [`android/README.md`](android/README.md) and
  [E11](../../docs/epics/E11-android-sync-adapter.md).
- **iOS waits for Phase 5** (ADR 0003): there is no `ios/` directory yet, and
  CI does not build one.
- **Toolchain pins**
  ([E02-R02](../../docs/epics/E02-repo-tooling-ci.md)): [`.fvmrc`](.fvmrc) pins
  **Flutter 3.47.6** (stable, Dart 3.13.5) and [`pubspec.yaml`](pubspec.yaml)
  pins the SDK (`Dart ^3.13.5`, Flutter `>=3.47.6 <4.0.0`). The Gradle wrapper
  (9.3.1) and JDK (21) pins for the `android/` module live in
  [`android/README.md`](android/README.md); the Android Gradle Plugin (9.1.0) and
  Kotlin Gradle Plugin (2.4.0) come from the pinned Flutter release.

## The scaffold (E10-R01)

Every dependency in `pubspec.yaml` is an exact pin and `pubspec.lock` is
committed. The app has just enough in it to prove the toolchain:

| Path | What it is |
|---|---|
| `lib/main.dart`, `lib/main_staging.dart`, `lib/main_prod.dart` | one entry point per flavor; each calls `bootstrap()` with its `Flavor` |
| `lib/bootstrap.dart` | loads the IANA timezone database and resolves the device's zone (E10-R04), then starts the app inside a `ProviderScope` that fixes the flavor and the device zone |
| `lib/src/flavor.dart` | `Flavor` (the `dev`/`staging`/`prod` API base URLs and issuers) and `flavorProvider` |
| `lib/src/app.dart` | `FlexCalendarApp` and the minimal home screen (flavor, API URL, session, readiness probe) |
| `lib/src/api/api_providers.dart` | `dioProvider` (with the E10-R02 auth interceptor), `restClientProvider` (the generated client, E02-R07) and `healthProvider` |
| `lib/src/auth/` | sign-in, tokens and sign-out (E10-R02); see § Sign-in |
| `lib/src/db/database.dart`, `database.g.dart` | the Drift database and its one table, `cachedCalendars` (generated by `drift_dev` through `build_runner`) |
| `lib/src/timezones.dart` | `initializeAppTimeZones()` (the single call to `timezone`'s loader), `initializeDeviceTimeZone()` (the native call) and `localZoneProvider`; see § Time zones |
| `lib/src/domain/time/` | the `TZID` layer: zone lookup, `WallClock`, RFC 5545 § 3.3.5's instants and the API's time shapes (E10-R04); INV-04's guard scans this directory |
| `lib/src/ui/` | the event-time renderer and the device-zone notice (E10-R04) |
| `lib/api/` | entirely generated (E02-R07); never hand-edited |

`newCachedCalendarId()` in `lib/src/db/database.dart` is the app's only id
generator, and it is a random UUIDv4 (INV-03). The `uuid` package is only ever
called as `Uuid().v4()`; `infra/scripts/invariants.mjs` rejects its non-v4
accessors.

## Flavors

The API base URL is Dart, not Gradle: the Android product flavor names the
build, the entry point picks the URL. A build or run therefore names both.

| Android flavor | Entry point | API base URL | Zitadel issuer |
|---|---|---|---|
| `dev` | `lib/main.dart` (the default target) | `https://api.localhost:8443` — the local stack, HTTPS on 8443 because rootless containers cannot bind 443 | `https://auth.localhost:8443` |
| `staging` | `lib/main_staging.dart` | `https://api.staging.flexcalendar.de` | `https://auth.staging.flexcalendar.de` |
| `prod` | `lib/main_prod.dart` | `https://api.flexcalendar.de` | `https://auth.flexcalendar.de` |

```sh
cd apps/mobile
flutter run --flavor dev \
  --dart-define=CALFLEX_OIDC_CLIENT_ID=… \
  --dart-define=CALFLEX_OIDC_PROJECT_ID=…
flutter build apk --flavor staging -t lib/main_staging.dart --debug
```

`--dart-define=CALFLEX_API_BASE_URL=https://…` and
`--dart-define=CALFLEX_OIDC_ISSUER=https://…` override the flavor's URLs for a
one-off build (a phone pointed at a throwaway host, or an emulator that reaches
the local stack through `adb reverse tcp:8443 tcp:8443`).

All three flavors keep the **one** application ID `de.flexcalendar.app` and no
`applicationIdSuffix`, because the OIDC redirect scheme is registered once
(PR #16, owner-approved).

## Sign-in (E10-R02)

Sign-in is OIDC **Authorization Code + PKCE S256** through
[`flutter_appauth`](https://pub.dev/packages/flutter_appauth) 12.1.0 against the
flavor's Zitadel issuer (D-03). The tokens live in
[`flutter_secure_storage`](https://pub.dev/packages/flutter_secure_storage)
11.2.0 and nowhere else — never in shared preferences, never in a log line, and
`AuthTokens.toString()` deliberately prints only the expiry.

Two values are generated by Zitadel and are therefore **not** in the source.
Both must reach the build as `--dart-define`s, and `oidcConfigProvider` throws
(`StateError`, the way `flavorProvider` throws) when either is missing:

- `CALFLEX_OIDC_CLIENT_ID` — the `android_client_id` output of the E02-R09
  configuration (`infra/zitadel/outputs.tf`, the application named
  `de.flexcalendar.app`);
- `CALFLEX_OIDC_PROJECT_ID` — the `project_id` output, for the audience scope
  `urn:zitadel:iam:org:project:id:<project_id>:aud` the API validates
  (from-E05-R01).

Scopes are `openid profile email offline_access` plus that audience scope.
`offline_access` is what makes Zitadel issue the refresh token the interceptor
rotates. The redirect URI is `de.flexcalendar.app:/oauth2redirect` and the
post-logout redirect `de.flexcalendar.app:/logout` (E02-R09), and the Android
scheme comes from the `appAuthRedirectScheme` manifest placeholder set to the
single application ID `de.flexcalendar.app` in `android/app/build.gradle.kts`,
since all three flavors keep that one ID.

| File | What it is |
|---|---|
| `lib/src/auth/oidc_config.dart` | the issuer, client id, project id, scopes and redirect URIs, per flavor, and the `dev`-only plaintext-issuer rule |
| `lib/src/auth/oidc_client.dart` | `OidcClient` (sign-in / refresh / end-session) and its `flutter_appauth` implementation |
| `lib/src/auth/token_store.dart` | `TokenStore` and the Keystore-backed `SecureTokenStore` |
| `lib/src/auth/auth_tokens.dart` | the token set and its expiry rule |
| `lib/src/auth/auth_interceptor.dart` | the `dio` interceptor |
| `lib/src/auth/auth_controller.dart` | `build` (the start-up restore), `restoreSession`, `signIn`, `signOut`, `handleSessionExpired` |
| `lib/src/auth/auth_state.dart` | `RestoringSession` / `SignedOut` / `SigningIn` / `SignedIn` |
| `lib/src/auth/sign_out_hooks.dart` | the hook list sign-out runs |
| `lib/src/auth/auth_providers.dart` | the providers, including `signOutHooksProvider` |

**TLS outside `dev`.** `OidcConfig.forFlavor` is the only way a build gets its
configuration, and it refuses a plaintext issuer for `staging` and `prod` with a
`StateError`, the way a missing client id is refused — the login carries the
user's password, and only the local stack is HTTP. A `dev` build pointed at an
`http://` issuer is the one case where AppAuth's `allowInsecureConnections` is
set; it is read from the configuration, never derived from the issuer at the
call site.

The one `dioProvider` carries an `AuthInterceptor` that

- refreshes a token that has expired or expires within 60 s **before** the
  request goes out, so an expiry mid-session is invisible to the caller;
- answers a `401` with one refresh and **one** retry;
- shares **one** refresh across all requests that need one at the same time;

and a refresh the IdP refuses (or an expired token with no refresh token) ends
the session.

**A relaunch keeps the session.** The first state of a new process is
`RestoringSession`, not `SignedOut`: the tokens are still in secure storage, and
`AuthController` puts them through `GET /me` (the same interceptor as every other
request, so an expired token is refreshed once there) before it tells the UI the
user is signed in. A refresh the IdP refuses, or a `401` the API answers, ends
the session through the same path as a manual sign-out, hooks included. A
sign-in or a sign-out taken while that check is running wins over it.

Sign-in itself calls `GET /me` immediately, because Zitadel refuses a token at
its own userinfo endpoint once the login session is gone (from-E05-R01). A `401`
from the API reaches the UI as the RFC 9457 problem, with its
`urn:uuid:<correlation id>` shown as a support reference (from-E05-R10).

Sign-out ends the session at Zitadel (RP-initiated logout with the ID token as
`id_token_hint`), clears the tokens, and runs every hook registered in
`signOutHooksProvider`. E10-R02 owns that list and the guarantee that all hooks
run (a hook that throws does not stop the ones after it); the offline cache
(E10-R03), the device keys (E12-R06) and, from Phase 4, the push token
(E07-R03) register into it. A sign-out whose end-session call fails still clears
everything locally.

### Live check (needs the local stack and an emulator)

The tests above replace the transport; they cannot prove the browser round trip.
With `make dev` up and the app installed on an emulator or device:

```sh
adb reverse tcp:8443 tcp:8443
cd apps/mobile
flutter run --flavor dev \
  --dart-define=CALFLEX_OIDC_CLIENT_ID=<android_client_id> \
  --dart-define=CALFLEX_OIDC_PROJECT_ID=<project_id>
```

Sign in, and the home screen shows the handle `GET /me` returned; then sign out
and confirm the app is back on the sign-in screen. **Close and reopen the app
while signed in** — it must come back signed in without the browser, which is
the part the tests below cannot reach. `flutter build apk --flavor
dev --debug` (what CI runs) exercises the manifest placeholder, and a `staging`
or `prod` build with `--dart-define=CALFLEX_OIDC_ISSUER=http://…` must refuse to
start.

## Time zones (E10-R04, INV-04)

Dart's `DateTime` knows only UTC and the device's local zone, so **no zoned
maths happens on a `DateTime`**: every `TZID` calculation goes through
`TZDateTime`, and the layer that does it is `lib/src/domain/time/`.

**The database and the device zone.** `initializeAppTimeZones()` (in
`src/timezones.dart`) is the one loader call; it loads
`package:timezone/data/latest_all.dart`, not `latest`, because only `latest_all`
carries the tzdata link names (`Asia/Calcutta`, `US/Eastern`) that the API
accepts as a `TZID` (from-E05-R09). `initializeDeviceTimeZone()` then reads the
device's IANA name through the native call (`flutter_timezone` 5.1.1, pinned)
and sets it as the package's local location. `bootstrap` awaits it before the
first frame and hands the result to `localZoneProvider`.

A name the database does not know — an unknown zone, a Windows name, Android's
`GMT+05:30` label — is **not** guessed at: it falls back to UTC, logs one line
carrying no user data, and returns a state the UI shows through
`DeviceZoneNotice` (on the home screen). `AppLocalZone.reportedName` keeps what
the device said, `null` when the native call itself failed.

The bundled database is tz **2026e**; the API's is Node's ICU, tz **2026b**
(from-E05-R09). They can disagree, so a `{local, tzid, utc}` read takes the
`utc` the API computed rather than recomputing the instant.

**The zone layer** (`lib/src/domain/time/`):

- `zones.dart` — `zoneFor`/`isKnownZoneName` (exact spelling, links included),
  `WallClock` (`YYYYMMDDTHHMMSS`, refusing what `DateTime` would normalise: 30
  February, hour 24, the leap second `60`), `parseUtcInstant`/`formatUtcInstant`
  and `instantOf`.
- `instantOf` gives **RFC 5545 § 3.3.5 form 3's** answers: a local time that
  does not exist (the spring-forward gap) is read with the UTC offset in force
  **before** the gap, and one that occurs twice (the fall-back hour) is the
  **first** occurrence. The `timezone` package's `TZDateTime(location, …)`
  constructor follows Java/Joda instead: the gap happens to land on the same
  instant, but the fall-back hour resolves to the *second* occurrence, which is
  why the app computes its own (`test/dst_table_test.dart` asserts both).
- `event_time.dart` — the three API shapes → `AllDayDate` / `ZonedTime`, and
  back (`apiJsonOf`). An all-day value is a date and has **no** instant
  (INV-04); a `TZID` the database cannot resolve keeps its wall clock and is
  flagged `zoneKnown: false` rather than silently rendered in a wrong zone.
- `src/ui/event_time_text.dart` — `EventTimeText`, the one renderer of a time:
  the device's zone by default (`tz.local`, which `initializeDeviceTimeZone`
  set), `2026-03-29 03:30 (GMT+2)`, and `2026-03-29 (all day)` for an all-day
  value.

**The guard.** `test/domain_time_guard_test.dart` walks every file under
`lib/src/domain/` with the analyzer and fails on a bare `DateTime(...)`,
`DateTime.now()`, `.toLocal()`, `add`/`subtract`/`difference` on a plain
`DateTime`, or `fromMillisecondsSinceEpoch`/`fromMicrosecondsSinceEpoch` without
`isUtc: true`. `AllowedUse` names an exception and its reason; the app's list is
empty, and `test/fixtures/zoned_datetime/planted_violations.dart` is the planted
bad file that proves each rule (and the allow-list) still bites. Add a domain
directory's file to `lib/src/domain/` and the guard covers it automatically.

**The DST runner.** `test/dst_table_test.dart` and `test/dst_widget_test.dart`
read `spec/ical-fixtures/dst/cases.json` itself — never a copy — and run every
case of E15-R02, comparing `expected` and, on a `view-zone` case,
`expectedLocal`. A `daily-skipped` case is compared like any other, per the
owner's ruling on RFC 5545 § 3.3.10 (`docs/02` § Recurrence). The widget tests
render each case in each of the four zones the Accept line names, with the
device zone set to each in turn; the counts per zone are printed by the run
(Berlin 18, New York 18, Sydney 18, Kolkata 16, plus Sao Paulo 16 and Chatham
18, whose half-hour and quarter-hour offsets are the traps).

### Live check (needs a device)

The tests run on the Dart VM, so the native zone call is only exercised through
its fallback there. On a device or emulator:

```sh
cd apps/mobile
flutter run --flavor dev
adb shell "su 0 service call alarm 3 s16 Europe/Berlin"   # or: Settings → System → Date & time
```

The app must show no `time-zone-fallback` line, and a time rendered on a DST day
must read the device zone's wall clock. Set the device to `GMT+05:30` or to a
zone name the database lacks and the notice must appear, with times in UTC and
nothing else changed.

## SQLite

No `sqlite3_flutter_libs` is declared: the package is end-of-life (`0.6.0+eol`)
and `sqlite3` 3.x builds the SQLite binary through Dart's native-asset build
hooks, which `drift_flutter` uses. `sqlite3_flutter_libs` still appears in
`pubspec.lock` as a transitive dependency of `drift_flutter` 0.3.1, so nothing
changes if a future `drift_flutter` drops it. `test/database_test.dart` opens a
real SQLite database in memory through `NativeDatabase`, which exercises the
Dart side of that path on the test host; the Android build of the same binary is
what `flutter build apk` in CI produces.

## API client generation (E02-R07)

`swagger_parser.yaml` reads `../../spec/openapi.yaml` (OpenAPI 3.1.0) and writes
`lib/api/`. This directory is entirely generated and replaced whole by `make gen`,
so files removed from the spec cannot linger.
Generator and runtime dependencies are exact pins in `pubspec.yaml`; transitive
versions are locked in `pubspec.lock`. Two pins are deliberately not the newest:

- `analyzer` 13.3.0 — build_runner 2.16.1 uses `contextFeatures`, removed in
  analyzer 14.x.
- `test` 1.31.1 — the Flutter SDK's `flutter_test` pins `test_api` 0.7.12 and
  `test` 1.32.0 requires 0.7.14, so the resolver rejects the newer one in a
  Flutter app.

With the pinned Flutter 3.47.6 / Dart 3.13.5 on PATH, run `make gen` at the root.
It runs `flutter pub get`, `dart run swagger_parser` (1.45.0),
`dart run build_runner build` (Retrofit, JSON serialization and Drift), then
`dart format lib/api`, through `infra/scripts/gen-dart.mjs`. The script moves the
old `lib/api/` aside first and puts it back, failing, when swagger_parser prints
"No schemes were generated" (1.45.0 exits 0 then) or leaves no Dart file, and it
refuses a path-level `parameters:` list in the spec before running anything,
because 1.45.0 dies on one. All generators are pure Dart; no JVM. Commit all
generated files and the lockfile. `make gen-check` detects stale, missing and
untracked generated files and runs through `make verify`.
