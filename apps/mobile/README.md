# `apps/mobile/` — Flutter mobile app

**Owning epic:** [E10 — Flutter mobile app](../../docs/epics/E10-mobile-app.md).

- **What belongs here:** one Flutter (Dart 3) codebase for Android (minSdk 26)
  and iOS 16+, with Riverpod, `dio` plus the client generated from
  [`spec/openapi.yaml`](../../spec/openapi.yaml), Drift (SQLite) for the offline
  cache, `timezone` for every `TZID` calculation (never raw `DateTime` — INV-04),
  and flavors `dev|staging|prod` (ADR 0002,
  `docs/02-technology-choices.md` § Mobile clients). The app is a REST client:
  it never talks to CalDAV itself, and it sends recurring-event edits as intents
  (INV-05).
- **`android/`** holds the Flutter project's Android module. From Phase 6 it
  also holds the native Kotlin `CalendarContract` sync adapter, with **no Dart
  in its sync path** — see [`android/README.md`](android/README.md) and
  [E11](../../docs/epics/E11-android-sync-adapter.md).
- **iOS waits for Phase 5** (ADR 0003): there is no `ios/` directory yet, and
  CI does not build one.
- **Toolchain pins**
  ([E02-R02](../../docs/epics/E02-repo-tooling-ci.md)): [`.fvmrc`](.fvmrc) pins
  **Flutter 3.47.6** (stable, Dart 3.13.5) and [`pubspec.yaml`](pubspec.yaml)
  pins the SDK (`Dart ^3.13.5`, Flutter `>=3.47.6 <4.0.0`). The Gradle wrapper
  (9.3.1) and JDK (21) pins for the `android/` module live in
  [`android/README.md`](android/README.md); the Android Gradle Plugin (9.1.0) and
  Kotlin Gradle Plugin (2.4.0) come from the pinned Flutter release.

## The scaffold (E10-R01)

Every dependency in `pubspec.yaml` is an exact pin and `pubspec.lock` is
committed. The app has just enough in it to prove the toolchain:

| Path | What it is |
|---|---|
| `lib/main.dart`, `lib/main_staging.dart`, `lib/main_prod.dart` | one entry point per flavor; each calls `bootstrap()` with its `Flavor` |
| `lib/bootstrap.dart` | loads the IANA timezone database once, then starts the app inside a `ProviderScope` that fixes the flavor |
| `lib/src/flavor.dart` | the `dev`/`staging`/`prod` base URLs |
| `lib/src/app.dart` | `FlexCalendarApp` and the minimal home screen (flavor, API URL, readiness probe) |
| `lib/src/api/api_providers.dart` | `dioProvider`, `restClientProvider` (the generated client, E02-R07) and `healthProvider` |
| `lib/src/db/database.dart`, `database.g.dart` | the Drift database and its one table, `cachedCalendars` (generated by `drift_dev` through `build_runner`) |
| `lib/src/timezones.dart` | `initializeAppTimeZones()`, the single call to `timezone`'s loader |
| `lib/api/` | entirely generated (E02-R07); never hand-edited |

`newCachedCalendarId()` in `lib/src/db/database.dart` is the app's only id
generator, and it is a random UUIDv4 (INV-03). The `uuid` package is only ever
called as `Uuid().v4()`; `infra/scripts/invariants.mjs` rejects its non-v4
accessors.

## Flavors

The API base URL is Dart, not Gradle: the Android product flavor names the
build, the entry point picks the URL. A build or run therefore names both.

| Android flavor | Entry point | API base URL |
|---|---|---|
| `dev` | `lib/main.dart` (the default target) | `https://api.localhost:8443` — the local stack, HTTPS on 8443 because rootless containers cannot bind 443 |
| `staging` | `lib/main_staging.dart` | `https://api.staging.flexcalendar.de` |
| `prod` | `lib/main_prod.dart` | `https://api.flexcalendar.de` |

```sh
cd apps/mobile
flutter run --flavor dev                     # lib/main.dart is the default target
flutter build apk --flavor staging -t lib/main_staging.dart --debug
```

`--dart-define=CALFLEX_API_BASE_URL=https://…` overrides the flavor's URL for a
one-off build (a phone pointed at a throwaway host).

All three flavors keep the **one** application ID `de.flexcalendar.app` and no
`applicationIdSuffix`, because the OIDC redirect scheme is registered once
(PR #16, owner-approved).

## Checks

`make verify-mobile` at the repository root is an alias of the component gate
`make verify-apps-mobile` (`node infra/scripts/verify.mjs apps-mobile`), so the
two can never drift apart. It runs, with the pinned Flutter on `PATH`:

1. `flutter pub get`
2. `dart format --output=none --set-exit-if-changed .`
3. `flutter analyze --fatal-infos` (`analysis_options.yaml` includes
   `package:flutter_lints/flutter.yaml`)
4. `flutter test` — `test/api_test.dart` (the generated client against a stub
   `dio` adapter), `test/home_screen_test.dart` (the home screen under a
   `ProviderScope` with the API client replaced), `test/database_test.dart`
   (the Drift round trip on an in-memory database, and the UUIDv4 shape) and
   `test/timezones_test.dart` (a `TZDateTime` in `Europe/Berlin` across the
   2026-10-25 changeover)

`flutter build apk --flavor dev --debug` is wired into CI
(`.github/workflows/verify.yml`), both in the path that runs for `apps/mobile`
changes and in the full run. It needs no signing key and no secret.

## SQLite

No `sqlite3_flutter_libs` is declared: the package is end-of-life (`0.6.0+eol`)
and `sqlite3` 3.x builds the SQLite binary through Dart's native-asset build
hooks, which `drift_flutter` uses. `sqlite3_flutter_libs` still appears in
`pubspec.lock` as a transitive dependency of `drift_flutter` 0.3.1, so nothing
changes if a future `drift_flutter` drops it. `test/database_test.dart` opens a
real SQLite database in memory through `NativeDatabase`, which exercises the
Dart side of that path on the test host; the Android build of the same binary is
what `flutter build apk` in CI produces.

## API client generation (E02-R07)

`swagger_parser.yaml` reads `../../spec/openapi.yaml` (OpenAPI 3.1.0) and writes
`lib/api/`. This directory is entirely generated and replaced whole by `make gen`,
so files removed from the spec cannot linger.
Generator and runtime dependencies are exact pins in `pubspec.yaml`; transitive
versions are locked in `pubspec.lock`. Two pins are deliberately not the newest:

- `analyzer` 13.3.0 — build_runner 2.16.1 uses `contextFeatures`, removed in
  analyzer 14.x.
- `test` 1.31.1 — the Flutter SDK's `flutter_test` pins `test_api` 0.7.12 and
  `test` 1.32.0 requires 0.7.14, so the resolver rejects the newer one in a
  Flutter app.

With the pinned Flutter 3.47.6 / Dart 3.13.5 on PATH, run `make gen` at the root.
It runs `flutter pub get`, `dart run swagger_parser` (1.45.0),
`dart run build_runner build` (Retrofit, JSON serialization and Drift), then
`dart format lib/api`, through `infra/scripts/gen-dart.mjs`. The script moves the
old `lib/api/` aside first and puts it back, failing, when swagger_parser prints
"No schemes were generated" (1.45.0 exits 0 then) or leaves no Dart file, and it
refuses a path-level `parameters:` list in the spec before running anything,
because 1.45.0 dies on one. All generators are pure Dart; no JVM. Commit all
generated files and the lockfile. `make gen-check` detects stale, missing and
untracked generated files and runs through `make verify`.
